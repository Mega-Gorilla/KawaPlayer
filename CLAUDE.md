# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

KawaPlayer is a fork of the VRChat video player [YamaPlayer](https://github.com/koorimizuw/YamaPlayer), adapted to integrate with the **VHub Playlist** service (`playlist.vrc-hub.com`). The purpose of the fork is to let world creators manage videos/playlists from inside VRChat: loading VHub playlists at runtime (PlaylistLoader module) and setting the world's auto-play default URL in-world (DefaultUrl module). All other player functionality is inherited from upstream YamaPlayer. Package name: `com.vhub.kawaplayer`.

- **Unity version**: 2022.3
- **Language**: C# / UdonSharp (VRChat's Udon scripting layer)
- **Dependencies**: VRChat Worlds SDK (>=3.10.2), Newtonsoft.Json (3.2.1)
- **Replaces YamaPlayer**: KawaPlayer keeps 152 of YamaPlayer's `.meta` GUIDs (scripts, U# programs, prefabs, animators, asmdefs) and its assembly names, so the two cannot be installed together. With both, the assemblies clash, and Unity rewrites on disk the GUIDs of the package it registers second, which stays broken after the other is removed (issue #319). `package.json` therefore lists YamaPlayer (`net.kwxxw.yama-stream`) in `legacyPackages`, which VCC removes when KawaPlayer is added, and an old `.unitypackage` copy (`Assets/Yamadev/YamaStream`) in `legacyFolders`. The shared GUIDs stay: changing them would break creators' scripts, add-ons written for YamaPlayer and the upstream sync.

## Build & Release

There is no local build command — the project is opened and compiled in the Unity Editor with VRChat SDK installed.

**Release workflow** (`.github/workflows/release.yml`, manual trigger with a `publish` checkbox):
1. Reads version from `package.json`
2. Packages into ZIP and UnityPackage formats (the UnityPackage is built by `.github/scripts/create-unitypackage.sh`), after leaving out what a world does not use: `docs/`, `CLAUDE.md`, `AGENTS.md`, `Assets/Models/Tablet/Source~/`, `Media~/poster/source/` (what the poster is drawn from; the poster itself ships) and `Tests/` (the list is in the workflow's "Leave Out What Is Not Part Of The Package" step; a new folder that is not for worlds goes there too)
3. Uploads both plus `package.json` as a workflow artifact — **without `publish` the run stops here (dry run)**
4. With `publish`: creates a GitHub Release with both artifacts **and an empty body** (refused unless run from `develop` and the tag does not exist yet). The release notes are added afterwards — see the checklist
5. With `publish`: triggers `repository-dispatch` to `Mega-Gorilla/vpm-repos` to rebuild the VPM listing

**VPM distribution** (`Mega-Gorilla/vpm-repos`):
- Built from VRChat's `template-package-listing` template
- `source.json` references `Mega-Gorilla/KawaPlayer` in `githubRepos`
- GitHub Actions auto-generates `index.json` from GitHub Releases
- Published at `https://mega-gorilla.github.io/vpm-repos/index.json`
- Users add this URL in VCC (Settings > Packages > Add Repository) to install/update KawaPlayer

**Required secrets**: `PAT` — Fine-grained Personal Access Token with `contents: read and write` permission on `vpm-repos`. `read-only` では `repository-dispatch` が `Resource not accessible` エラーで失敗する。

**Version format**: 独立した SemVer (`Major.Minor.Patch`)。`1.0.0` から開始。
- KawaPlayer は独立パッケージのため、upstream YamaPlayer のバージョンには従わない
- upstream のベースバージョンは `Assets/updatelog.txt` とコミット履歴で追跡する
- SemVer の pre-release 識別子 (`-beta`, `-kawa` 等) を含むと VCC で「Show Pre-Release Packages」を ON にしないと表示されないため、正式リリースでは使用しない

**Two changelogs, two audiences**:
- `Assets/updatelog.txt` — **表示されるのはワールドの中**。`ScreenUI.prefab` と `Tablet.prefab` が `UIController._updateLogTextAsset` として参照し、プレイヤーの Info パネルとタブレットのバージョン情報にそのまま出る UI テキスト。読むのは遊ぶ人なので、**直近 3 回の版の変更**を、新しい版から順に、遊ぶ人に見えるものに絞って版ごとに数行で書く（SDK・モジュール管理・ビルドのログなど、制作者向けの話は書かない）。リリースのたびに新しい版を先頭に足し、4 つ目より古い版は消す（2026-10-19 に、その版だけから直近 3 回に変えた）。遊ぶ人に見える変更がない版は「不具合を直しました」の 1 行でよい。日本語のみ、リンクや issue 番号は書かない。少しくだけた口調でよい
- `docs/releases/<version>.md` — **GitHub Release の本文**。読むのはワールド制作者と、自分のスクリプトから KawaPlayer を呼ぶ開発者なので、詳しく書く。`updatelog.txt` の転記ではなく独立した文章にする。口調は VRChat のリリースノート（例：`https://docs.vrchat.com/docs/vrchat-202631`）のように、短い箇条書きに、ときどき一言の冗談を混ぜたくだけたもの。並べ方は `docs/releases/1.3.0.md` を前例とする: 目玉を冒頭で一言 → 更新する前に必ずすること（SDK・ビルドし直し・名前の変更・消した API）→ 新しいこと → 変わったこと → 直したこと → 中身の改善 → 自分のスクリプトから呼ぶ人へ → 困ったら（既知の問題の列挙はせず Discord へ、`https://discord.gg/tkrHek6PvN`）→ 入手方法（VCC のみ）→ 全部の変更（前の版との compare のリンク）→ 英語のまとめ。項目の末尾に PR の番号を付ける。`vcc://vpm/addRepo?url=...` はコピー用のコードブロックで書く — GitHub の Markdown は `vcc://` の href を落とすので、リンクにしても押せない。**UI で分かる変更（インスペクター・ワールドの画面・メニュー）には画像を付ける**（2026-10-23 ユーザー指示）: 画像は `docs/releases/images/<version>/` に WebP で置き、その項目の小項目の下に載せる。Release の本文は相対パスを解決しないので、画像を足したコミットの SHA で固定した `https://raw.githubusercontent.com/Mega-Gorilla/KawaPlayer/<SHA>/docs/releases/images/...` で書く（画像を先にコミットしてから、その SHA で本文を書く）。PR に載せた画像（`pr-assets`）から作ってよい。版の番号が写った画像は、写らないように切る。ビルドのログやエラーの文は、画像ではなくコードブロックで実際の文を見せる
- `docs/releases/README.md` — 版の一覧。1.1.2 までの版は GitHub の Release に本文がない（1.1.0・1.1.1 は Release もない）ので、ワールドの中の更新履歴にあった内容をここに残している
- `docs/**/*.meta` は `.gitignore` 済みなので `.meta` は作らない。`docs/` はリリースの zip にも `.unitypackage` にも入らない（`release.yml` で除く）。使い方ガイドなどは GitHub で読む

**Release checklist**:
1. `package.json` の `version` を更新
2. `Assets/updatelog.txt` の先頭に新しい版を足し、直近 3 回の版だけを残す（遊ぶ人に見える主な変更だけを版ごとに数行）
3. `docs/releases/<version>.md` を書き、`docs/releases/README.md` の表に足す（上記の作法。レビューは PR で受ける。日付はリリースの日に両方へ入れる）
4. コミット・push
5. GitHub Actions の「Build Release」ワークフローを **`publish` にチェックを入れて**手動実行 (develop ブランチ)。チェック無しで実行すると成果物を Artifacts に上げるだけの dry run になる (ワークフロー変更の確認に使う)
6. リリースが作られたら本文を入れる: `gh release edit <version> --repo Mega-Gorilla/KawaPlayer --notes-file docs/releases/<version>.md`（ワークフローは本文を付けない。添付資産には触れない）
7. repository-dispatch → vpm-repos listing 再ビルド（`index.json` に新バージョンが載る）を確認

Published VPM versions must not be deleted (breaks projects using source control).

## Compatibility & Technical Debt Policy

実装・レビューの共通ルール（ユーザー合意、2026-10-15）。

- **旧版との互換性より、現行仕様に沿った単純で一貫した設計を優先する。** 旧バージョンの内部実装・挙動を維持するためだけの互換コードは原則不要とする。
- 公開済みワールドにはビルド時の KawaPlayer が組み込まれており、新しいパッケージを公開しただけでは差し替わらない。更新・再アップロードしない旧版ワールドの動作を守る目的で、新版に旧処理を残さない。
- 変更範囲の不要なコード・暫定分岐・二重実装・ラッパーは削除し、互換性を理由に技術負債を温存しない。未公開版間の互換性維持や移行処理も原則不要とする。
- **既存プロジェクトを新版へ更新したあとの動作確認は行う。** シーン・Prefab の参照、設定、プレイリスト、永続化データへの影響を確認する。破壊的変更や移行・再設定が必要な場合は、その影響と手順を PR・利用者向けドキュメントに明示し、旧実装を恒久的に残すことで対処しない。
- レビューでは現行仕様の正しさ・設計の単純さ・更新後の動作・変更点の案内を評価する。旧版の内部実装や挙動と違うことだけを理由に差し戻さない。一方、具体的な参照切れ、意図しない設定・データの消失、コンパイル・ビルドエラーは不具合として指摘する。
- この方針は Unity / VRChat / Udon の制約を無視する許可ではない。Unity の `.meta` / GUID、Network ID、宣言した SDK 対応範囲、現行版の PC / Quest 間の整合性に関するルールは引き続き守る。

## Architecture

### Core Runtime (`Runtime/Internal/`)

**Controller** (`Controller.cs` + partial files) — Central UdonSharpBehaviour managing:
- Playback state machine (Idle, Playing, Paused) with network sync via `[UdonSynced]` fields
- Multiple video player handlers with automatic fallback on error
- Owner-based authority model (VRChat networking)

Every client places the video by the same clock: the owner shares a video time and the server time it was taken at (`_syncedServerTimeMs`, from `Networking.GetServerTimeInMilliseconds`, 0 while there is none), and the time since is worked out with `Networking.CalculateServerDeltaTime`, which takes seconds and copes with the value wrapping. `GetNetworkDateTime`, used before, stays on the local clock on a client whose date sync fails (VRChat logs `Failed to sync network DateTime`), and that client played off by its clock's error for good (issue #237). A new track goes out with no shared time, and its owner shares 0 when it is ready; a reload, a retry after an error, or a load an owner took over while it was loading, is placed by the time already shared (`AfterVideoReady`), since sharing 0 then sent everyone back to the start (issue #234). Each client checks its video against the shared time once a second and seeks only when it is 0.9 s of real time off, and not while the video has not moved since the last check (buffering, where a seek would throw away what has loaded); placing a video when it gets ready, and when a new shared time arrives, is exact (issue #235). Following the shared time never shares one (`SeekLocal`): only a seek by the user (`SetTime`) does. Reload is each player's own and sends nothing (issue #232): it also brings back a video stopped on an error, or one still loading 15 s after the load began (a slower load is left alone), but not while the shared state is stopped, and the reload button shows when it would do something. A non-owner reloads the track and player it was sent; the owner and local mode reload their own `Track`, since the synced copy is made only when sent. Reloads and retries are kept 5.1 s apart, requests while waiting making one reload: a request is dropped when a retry or a new track has loaded since it (two loads at the same 5.1 s otherwise), one made after that load runs 5.1 s after it, and the reload a change of speed or resolution needs waits for a load under way (`ReloadForSettings`). A creator can place a Global Reload Button (`Modules/GlobalReload/GlobalReloadButton.prefab`, **GameObject > KawaPlayer > Global Reload Button**, issue #236) for a live event, where a stream is not placed by the clock and players fall behind each by their own amount: it has every player reload its own video, as if each had pressed reload, and sends only a network event, from the GlobalReload module the creator adds to the player in Module Manager (issue #248; see Modules below). One press sends, as on VizVid's Global Sync Button: who may press it is settled by where it stands and, with PermissionManagement, by Editor or above. It then waits 15 s, dimmed (the time a player leaves its own load alone). It looks like a hexagonal LED display, its dots running to the edges: lit dots draw a ring with two arrows chasing each other round, and a strip of 5 x 7 dot words across the middle, through the gaps between the arrows, says its state, in English only: RELOAD ALL, RELOADING (for the 15 s after a send), NO VIDEO (everyone stopped), and NO ACCESS over a red cross. It asks for the permission once a second as a press would (`BeforeUserGlobalReload`), so a player who may not press it sees the cross first. The pictures (`Modules/GlobalReload/Images/global-reload*.png`) are white shapes tinted in Unity; the cross and its words are red, with no palette role, so they stay red whatever colour set the world uses. The screen and the tablet have no such button, as it is seldom needed. The whole design, and how it was decided, is in `docs/design/228-playback-sync/`; the sync as built is in `docs/analysis/playback-sync.md`. A synced field whose type changes keeps instances of older builds apart (VRChat's network compatibility check), but PC and Android are separate builds that meet in one instance: when the synced fields change, both have to be rebuilt.

**Handler System** (`Handlers/`) — Abstraction over video backends:
- `PlayerHandler` — abstract base
- `BaseVideoPlayerHandler` — wraps VRC's built-in video players
- `ImageViewerHandler` — static image display

**UI System** (`UI/UIController.cs`) — Manages all interactive controls (play, pause, seek, volume, speed, playlists, modals). Heavy use of serialized fields for Unity inspector binding. The playlist tabs (Queue, History, Playlist, on the screen, the tablet and the Playlist Panel) are the only controls whose look changes through an Animator: `Assets/Animators/Toggle/Toggle.controller`, YamaPlayer's own, lifts a tab's label by 3 while it is pointed at. Upstream had turned that file into the UI lock's controller and then replaced it, leaving the tabs pointing at nothing, so it was put back with the GUID the tabs still referenced (issue #246).

**Screen controls** (`Prefabs/UI/ScreenUI.prefab`, issue #258) — The screen's controls sit in one bar at the bottom (`Canvas/User/Main/Bottom`), over a gradient that darkens towards the bottom: the seek row, and under it three groups in `Bottom/Controls`: `Left` (URL, loop, shuffle, ReSync), `Actions` (back, play or pause, next, stop) and `Right` (volume, list, settings, and More, which opens a small panel with Info and the UI lock). The groups' layout groups size every button from its `LayoutElement` (84, play and pause 104), so a size a scene or a prefab saved over an older layout still comes out right. A button's own Image is its round ground (`bar-circle.png`) and its icon is the child `Image`. Texts that only decorate (the title card's lines, the seek bar's times, a button's name) take no presses. Buttons in a group (the bar, its volume and More panels, the list's header and strip, a track's actions) show their icon only: the ground is the Selectable's target, clear until pointed at, when it shows as a light grey ring. The bar's buttons are pressable only when pressing would do anything (`UIController.UpdateControlsView`, ReSync in `Update`): not play and stop while stopped (stop still clears an error), not back without a place in a playlist, not next without that or a track in the queue, and not ReSync while it would do nothing (#232). A ring shows it by dimming its icon and the filled play by fading its ground (`SetPressable`), as a ring's ground no longer can. While stopped, the URL field is the main action and shows a filled ground (its child `Emphasis`: Primary, with an OnPrimary icon), the play button being the faded one. The bar's play and pause keep a filled ground, the one filled button on the screen, and the buttons that stand alone ("∨", the settings page's back) keep their grounds; the name shown while a button is pointed at is its `Tooltip`, slid in by the `FrontButton` animator above the seek row. The bar's images (`Assets/Images/bar-*.png`) are drawn by `docs/design/258-screen-ui/images/bar_icons.py`; `bar-copy.png` (the usual copy icon, two sheets) is the icon of every URL shown to copy: the strip's, a track's, and the dialog's copy field. The More panel opens and closes on the `More` layer of the `UI` animator (`ToggleMore`, and `HideMore` from the buttons that open something else). It is `Right/MorePanel`, the More button's sibling for the reason the volume panel is its button's (below), pinned to the group's top right, where the More button ends the group, and kept out of the group's layout (`LayoutElement.ignoreLayout`). The volume button (`Right/Volume/Button`, its icon swapped for `Muted` while muted) opens the volume panel above it (`Right/Volume/Panel`: the volume as a percentage, the upright bar and the mute buttons) on the `Volume` layer (`ToggleVolume`, and `HideVolume` from More, the list and settings; the volume button sends `HideMore`), so one of the two is open at a time. The panel is the button's sibling, not its child: a press in a button's child reaches the button, and would close the panel. `SliderHelper` reads a bar taller than it is wide from the bottom up, and the volume bar's rect is the knob's travel (the track and the knob reach past its ends), so the Slider and the helper read a press at the same height as the same volume. The rect is 84 wide, the least a press needs, while the track is 16 and the knob 56 (an upright Slider stretches its knob across the rect, so the knob's width is set 28 short of it). A knob takes presses over 84 through its raycast padding, larger than it is drawn: this one, the seek bar's (26 x 36) and the settings' (#318); the helper shows its pressable strip only inside that rect. The list is a square panel down the right edge, 600 wide and the screen's full height (`RightSide/Playlists/Main`, the shared list below, drawn over the bar), that the bar's list button slides up from below (`TogglePlaylist`, on the `Playlists` layer; More sends `HidePlaylist`, and the list button clears a `HidePlaylist` left waiting; the volume button does not close the list, as its panel opens beside it). While it is open the bar narrows to what the panel leaves: the `Playlists` clips end the seek row (`Bottom/ProgressBar`) at the panel, move the playback buttons (`Controls/Actions`) to the middle of what is left and the volume and list buttons (`Controls/Right`) to the panel's edge (the group is as wide as its buttons and is moved by its left edge, so the tablet, which hides settings and More, stops them in the same place), drop the left group (URL, loop, shuffle, ReSync) out of view, and fade settings and More out (a `CanvasGroup` on each, which also stops their presses); closing brings them back. The list closes from the bar's list button, from its "∨" (`RightSide/Playlists/Close`, the screen's own, a round 84 like the bar's buttons, laid over the list's bottom right in the bar's row of buttons; the list runs on under it), or from a press anywhere outside it (`Main/ListShade`, a see-through button the layer switches on with the list, under the bar so that the bar stays pressable), all sending `HidePlaylist` (the list button through `TogglePlaylist`). Its tabs are three segments 64 high with an icon, across the list's width, so a long translation needs a short word (Spanish says "Listas"); a tab's label stays a direct child of its toggle, whose animator lifts it by 3 while pointed at. In a playlist, the header (`Top/Info`: back, name, track count and "…") shows under the tabs, and "…" opens the strip of the playlist's actions under it (`Info/ActionStrip`: refresh, URL, delete, on the same island as a track's actions: Surface, 76 high, its buttons 64 but pressable over 84); the `UIController` shows and hides both itself (`_playlistHeader`, `_playlistActionStrip`): a playlist's row opens it through `OpenPlaylist` (the tracks' page first, then its rows, as a row's animator told to reset while inactive logs an error), "…" is `TogglePlaylistActions`, and opening a playlist closes the strip. Leaving a playlist's tracks, by the back button, the queue or history tab, the playlist tab (pressed again too: a toggle on in its group still calls back, and the tab's only page switch is `UIController.OpenPlaylistsTab`, which goes back the way the back button does), or the playlist being taken away, closes the header and the strip together (`UIController.HidePlaylistHeader`). As the list's height is set by the panel's layout (0 before its first pass, and changing with the header and the strip), `LoopScroll` makes lines for the larger of its own height and its canvas's. A list just opened (a playlist, the queue or the history tab) is drawn from its top in one pass (`LoopScroll.SetUpAtTop`); a redraw leaves its lines on, as switching a line off and on runs OnDisable and OnEnable on all it holds, its buttons' Udon behaviours included, and switches off only those left empty; and a scroll within the same lines draws nothing, the two arrays it compares being swapped rather than made anew (#310). The `UIController` finds the parts of each line (texts, marks, actions, animator, `IndexTrigger`) once, when the lines are first drawn (`FindTrackLineParts`, `FindPlaylistLineParts`, #326). "…" and the URL button show only for a playlist loaded in the world (`DynamicPlaylist`), the URL button showing its source in the dialog's copy field, as a baked playlist keeps no URL at run time. A track and a playlist take one line 84 high, and pressing a track slides its actions up over it (icons on an island, `Actions/Island`, with play on a tonal ground: PrimaryContainer, its icon Primary; each 64 across but pressable over 84 through its raycast padding): the `TrackAction` animation collapses the track's info by those 84, and as the Playlist Panel shares that animation, its rows are 84 too. The hidden actions sit right at the edge of the row's mask, where a line of them would show, so they are see-through until shown: the clips also fade a `CanvasGroup` on `Actions` in as they slide up and out as they go. A `RectMask2D` re-culls every graphic under it each frame, still or not, so the row's mask and its `Info`'s are on only while the actions show or move: the clips switch them, with `Actions`' `blocksRaycasts`, as the row's mask was also what kept the hidden actions from taking the next row's presses (#325). The list's own ground takes presses and does nothing, so a press in its margins does not reach `ListShade`; inside it only the rows and the buttons take presses: a playlist's row over its whole line (a clear Image is its button's target), like a track's, while the texts and marks that only decorate (the tabs' labels and marks, the header's name, a row's number, title and folder) take none. A track's URL action, like its other actions, calls the `UIController` through the row's `IndexTrigger` (`ShowPlaylistTrackUrl`), which shows the track's title and its URL in the dialog's copy field; a UI without a dialog does not show the action (#318). Nothing darkens the whole screen while the controls show: only what is read over the video has a ground of its own (the title card, the bar's gradient, and the list panel), and the settings page darkens what is behind it with `Pages/Shade`, over the page's blur. The title card top left is `Main/Top/Card`, sized to what it shows by its layout groups: `VideoInfo` stacks the lines at their scaled size (the texts are drawn at 0.2, so its layout group uses the children's scale), an empty URL line is hidden, and `Main/Top`, which stays where the `FrontControl` animation puts it, caps the card at its own width (1000), where a long line is cut by `VideoInfo`'s mask. While nothing is loaded the card shows the logo (`_trackInfoLogo`) beside the player's name and version, and under them what the URL input accepts (`_urlHintText`). Under a title, its second line is the playlist and the place in it ("name · 3 / 8", from `Controller.ActivePlaylist` and `PlayingTrackIndex`) while a playlist's track plays, else the URL. A refresh or a delete of that playlist, or a sync of the indexes alone, changes it while the track stays, so the card is also redrawn on `AfterPlaylistsUpdated` and `AfterTrackSynced`. The dialog (`Modal`) is drawn at 1, so its texts are 20 and over, as every text of the screen. A UI without that logo (the Controller Bar) leaves its title empty then. The `FrontControl` layer moves the card and the bar out of the way while a page is open and puts them back, writing their places, so a change of their place goes into `ShowFrontControl.anim` and `HideFrontControl.anim` too. The tablet hides Settings, Info, the lock and More. The settings page is the shared settings below (`Pages/Settings`); the page keeps its own back button (`Pages/Return`, a round button top left), its shade and the Info page, and moves the settings' heading right of the back button. The settings close from that button only: a press is taken by the nearest part above it that takes one, and a slider or a scrollbar takes no click, so a button over the whole page closed the settings whenever one was let go (#318). The Info page (`Pages/Version`), which has no controls, also closes on a press on its ground: a clear Image whose raycast padding reaches the page's sides carries the closing button. A `RectMask2D` re-culls every graphic under it each frame, still or not, and `Main`'s, which hides what waits off the screen (the closed list, the left group dropped while the list is open, the card and the bar moved away for a page), covered the list too (#325). So the list's side (`Main/RightSide`) is a canvas of its own, sorted over its parent (`overrideSorting`, order 1), which `Main`'s mask does not reach: the `Playlists` clips switch that canvas on while the list shows or moves and off once it has slid away, and the side's own `RectMask2D` on only while it slides, so the list is cut at the screen's edge then. Anything drawn over the list sorts over it too: the dialog (`Modal`) is a canvas of order 2. The plan, and the step still to come (the finish), are in `docs/design/258-screen-ui/`.

**Settings** (`Prefabs/UI/Settings.prefab`, issue #309) — The screen's settings page and the tablet's settings app are one prefab, its controls wired to each UI's own `UIController` fields, so both offer the same items, the Global ones included: categories on the left (Playback, Video, Audio, Language, and Permission when PermissionManagement adds it), a card per item on the right (title, description, control, sized to their text by layout groups), and under the pages a note on what (Global) means. A title's "(Global)" is drawn at 26 beside its 36 (`UIController.GlobalSuffix`, which the pitch and slide show rows use too, and the DefaultUrl card's `_globalSuffixSize`). `SettingsPanel` (`Runtime/Internal/UI/`, on the prefab's root) translates what the UIController does not (its title, the category names, the note) and, on a tablet held upright, lays the categories out as tabs along the top, the icon over the name, again when one shows or hides (the permission tab shows only to an Admin). A module puts a row or a category into it with a slot whose path starts at the settings (`ModuleUISlot.inSettings`, found from each `SettingsPanel` under the UIController), so one slot reaches the screen and the tablet; the U# that drives a module's row sits on the row (AudioLink, pitch, the DefaultUrl card), except `SlideShowerUI`, which also holds the seek bar in slide mode and so sits where it always runs (`Canvas/User`, `Canvas/Display`). It replaced the screen's `SettingPanel` and its row prefabs, and the tablet's own settings app, whose objects carried network IDs in the worlds built with them: the build's network ID step leaves out a record whose object is gone (`SetError.InvalidObject`), and stops only for an object that stays and changes its Udon parts.

**List** (`Prefabs/UI/ListPanel.prefab`, issue #315) — The screen's list and the Playlist Panel are one prefab: the tabs, a playlist's header and the strip of its actions, the playlists and the tracks, and the rows' actions, wired to each UI's own `UIController` fields (the same 19). Each UI points the two row templates' `IndexTrigger` at its own `UIController` (an override on its instance), as a nested prefab cannot point outside itself; for the same reason nothing in the list calls into a UI's animator, and the `UIController` shows the header and the strip itself. The tabs take the list's whole width, on the screen as on the Playlist Panel. The Playlist Panel is the list alone in one column, 600 x 900 at its old scale (0.67 m x 1.00 m), on an opaque ground, with no dialog, so its "…" and a track's URL action stay hidden (decision D8): refreshing, the URLs and deleting are done on the screen and the tablet.

**Playback error details** — When a video fails, the screen's error message has a "Details" button that opens the last errors in the dialog, and asks for a screenshot on Discord. A world cannot open a link in VRChat, so the Discord address is in the dialog's copy field (`Modal.ShowCopyField`, an InputField the viewer can copy from). `Controller.ErrorReport.cs` keeps the last five, per viewer and unsynced: it records each failed try before the retry logic switches handlers, and numbers the matching log line; `UI/UIController.ErrorDetails.cs` builds the text. A handler can say more than its `VideoError` through `PlayerHandler.ErrorDetail` (the image viewer gives the downloader's error). For Access Denied, the screen asks the viewer to turn on Allow Untrusted URLs and, if the video still will not play, to ask the world's creator: in Public and Group Public instances an untrusted site plays only when the world lists it in its Video Player Allowed Domains, which only the creator can change (issue #225). The details then add, under the latest error, a note for the creator naming the domain to add. A picture needs only Allow Untrusted URLs, so the image viewer's Access Denied gets no note.

**Which player a URL plays on** — A URL entered in the world plays on AVPro unless someone chose the image viewer in the settings (issues #139, #182). `Controller` records whether the player in use was switched to by a track rather than chosen (`HandlerFromTrack`, synced): a picture from the tablet, a URL played on the player picked for it in the URL dialog, or a playlist's or the queue's track on another player, leaves it switched, and then the URL field, the URL dialog's selector and the settings all offer AVPro (`UIController.OfferedPlayerType`), so the next URL does not load as a picture. A player picked in the URL dialog is for that URL only; choosing one in the settings (`Controller.SetPlayerType`) keeps it for the URLs entered next, even the image viewer a picture had switched to already, which needs no question since nothing stops. A player starts on AVPro, the first of its video players. A track whose own player is missing, or refuses its URL, plays on the first in the order AVPro, Unity, image viewer that takes it; an error during playback switches through each player's own fallback (`_fallbackHandler`, AVPro and Unity to each other), whatever the order. The inspector offers no choice of player, and `VideoPlayerOrderBuildProcess` sorts every `Controller`'s players into that order at build and on Play, whatever order a scene saved (issue #166). A VHub track that names Unity (mode 0, or no mode) loads as AVPro, both at run time (`PlaylistLoader`) and when imported in the Playlist Editor. A playlist imported from VHub (`PlaylistItem.vhubPlaylistUrl`) has its Unity tracks baked as AVPro (`PlaylistBuildProcess.BakedPlayerType`), so one imported before #166 plays on AVPro once the world is built again, without its saved tracks changing; each track's origin is not kept, so a track meant for Unity goes in a playlist not imported from VHub, as the Playlist Editor notes. Any other playlist's Unity track still plays on Unity.

**Appearance** (`Runtime/Appearance/`, `Editor/Appearance/`) — KawaPlayer's colours are kept in one asset, `Assets/Appearance/KawaPlayerPalette.asset` (`ColorPalette`): the colour sets (KawaPlayer's first, then YamaPlayer's five) and the neutral colours. Each UI's `AppearanceSettings` points at it and picks a set by name (KawaPlayer's by default; a name no set has gets the first). Graphics carry a role (`ColorDefinition`) instead of a colour, and `AppearanceBuildProcess` colours them when the world is built; a button whose colour comes from its tint has the tint moved instead. To change a colour, edit the palette; "Apply Colors Now" on an `AppearanceSettings` also updates the colours saved in a prefab. Give new UI a role rather than a literal colour. The screen's idle image (待ち受け画像, `UIController._idleScreenSprite`, shown while stopped or loading) is `Assets/Images/default-idle-screen-image.png` by default, set on `ScreenUI.prefab`; a world creator can swap it in the KawaPlayer inspector. That image is only the background, 128 x 72 and stretched (uncompressed and without mipmaps, as block compression would show); the logo and the name are drawn over it by `IdleImage/IdleLogo`, which `UIController` shows only while the sprite is the default one (`_defaultIdleScreenSprite`), so an image the creator chose is shown alone (issue #189). They sit in the middle of the screen, with the image's glow behind them (#258); the loading icon, the error message and the Details button draw over them there, which was accepted.

**Logo and images** — KawaPlayer's logo is one white image, `Assets/Images/kawaplayer-logo.png` (1024 x 1024, crunched), coloured where it is used: white on the idle screen, silver on the back of the tablet. The logo's original images (white, black and gradient, reduced from 8192 x 8192, with faint leftovers of its editing cleared) are kept in `Media~/logo/`, with the quick start poster and its source in `Media~/poster/`: material creators may use to show KawaPlayer, under terms of its own rather than the package's (`Media~/LICENSE.md`, issue #196). Unity does not import `Media~`; the zip carries it, the `.unitypackage` does not. Keep what images cost in a world small: the icons are crunched and at most 512, and an image with mipmaps whose sides are not powers of two cannot be block-compressed, so Unity keeps it uncompressed (the old 1920 x 1080 idle image took 8 MB). An image nothing references is not built into a world, but is still in the package, so delete it.

### Extension Pattern

`YamaPlayerListener` (base class) provides virtual callback methods (AfterVideoReady, AfterVideoStarted, AfterVolumeChanged, etc.) that modules and custom scripts override to react to player events.

### Modules (`Modules/`)

Each module is an independent assembly with its own `.asmdef`. Modules extend the player via the listener pattern and are optional dependencies.

A module's `YamaPlayerModuleDefinition` may sit deeper than directly under the player's `Modules` (DefaultUrl's is on `Modules/DefaultUrl/Controller`, beside its storage). Module Manager and the player inspector list every module under `Modules`; switching one off switches off its root, so its other parts go with it. The root (`YamaPlayerModuleBuildProcess.GetModuleRoot`) is the module's own object, or the one its definition names in `moduleRoot` when its parts sit beside it — DefaultUrl names `Modules/DefaultUrl`. It is never worked out from what else shares a folder. The DefaultUrl settings card is the module's own, a template under its controller that the module's slot puts into the settings, so a player whose DefaultUrl is missing or switched off has no card. The build leaves out a module whose own object or root is off (`IsModuleEnabled`), and the duplicate warning, the module translations and the autoplay check follow the same rule. DefaultUrl and AutoPlay both start a video on join with nothing deciding between them, so having both on one player is reported as an error in Module Manager, the player inspector and the build log (the build goes on, as for a duplicate). A module that comes with the prefab (KawaPlayer's own PlaylistLoader and DefaultUrl) cannot be deleted from the list, only switched off: there is no standalone prefab to add it back from.

KawaPlayer-specific modules (the reason this fork exists):
- **PlaylistLoader** — loads playlists from `playlist.vrc-hub.com` at runtime using the Pre-baked URL Pool pattern (see Key Constraints below). Design docs: `docs/design/url-pool/`. VRChat plays VHub's tracks in Public and Group Public instances only if `playlist.vrc-hub.com` is in the world's Video Player Allowed Domains, which the creator sets on VRChat.com (Edit World Info), not in Unity, and the listener has Allow Untrusted URLs on: the domain alone is not enough; other instances need only each listener's Allow Untrusted URLs. Loading a playlist in the world is a string download, which always needs each player's Allow Untrusted URLs.
- **DefaultUrl** — lets the Instance Owner set the world's auto-play video/playlist URL from inside VRChat, synced to all players and persisted across visits. Users never see "DefaultUrl" or "default URL" (issue #173): the in-world settings card is titled 自動再生(Global) (Autoplay (Global)), with the "(Global)" every setting that reaches the whole instance carries, drawn smaller than the title as on the other Global items (`_globalSuffixSize`; #173 had dropped it and #216 put it back), and Module Manager lists it as 自動再生(Owner), beside AutoPlay's 自動再生(World). Only these display names changed; the class, folder, object and translation-key names (`module.defaultUrl.*`, `module.autoPlay.*`) and the saved storage stay as they are, so worlds and saved URLs carry over
- **GlobalReload** — has every player reload their own video, for a live event (issues #236, #248). It syncs nothing but is `Manual`, as a behaviour that does not sync sends no network events; its `Send` sends `OnGlobalReload` to all, which runs each player's own `Controller.Reload`. The button a creator places (`GlobalReloadButton`, on the button prefab's `UI/Canvas/Button`) does the pressing, the four states and the permission check; `GlobalReloadBuildProcess` links each button to the GlobalReload module of the player its `UIController` follows, and a button with no player, or whose player has the module missing or switched off, is switched off and tagged `EditorOnly` with a warning in the build log. The core `Controller` and `UIController` know nothing of it. Module Manager lists it as 全員リロードボタン (Global Reload Button), the button's name in the guide (#247)

Inherited from upstream YamaPlayer:
- AudioLinkAdaptor, AutoPlay, LTCGIAdaptor, LightVolumeAdaptor
- PermissionManagement, Persistence, PitchShifter, SlideShower
- TimelineSync, VideoInfoDownloader

### Prefabs

`KawaPlayer.prefab` at the repository root is the main all-in-one prefab that users drop into scenes (also reachable via the **GameObject > KawaPlayer > Main** menu). Additional prefabs (ControlBar, PlaylistPanel, SubScreen, Tablet, UI parts) live in `Prefabs/`; the Global Reload Button lives with its module in `Modules/GlobalReload/`. The Tablet's scripts (`TabletPickup`, `TabletScreen`, `TabletReturnButton`, and one per app: `TabletImageApp`, `TabletVisitorsApp`; the settings app is the shared settings above) live in `Runtime/Internal/Tablet/`; its model and Blender build script in `Assets/Models/Tablet/`. The settings app's controls are wired to the tablet's own `UIController`, and modules add their rows to it through the same settings slots as to the screen's. PermissionManagement puts its listener under the tablet's `Canvas/Display` the same way, so its permissions apply to what the tablet plays; that slot reuses the listener template of its slot for the screen (`Canvas/User`), and the build copies it into each UI that has the slot's path. A small UI with no such place keeps an empty `Canvas/Modules` for it: the Global Reload Button, a `YamaPlayerSubController` over a `UIController` that has only the button (as the Controller Bar has only its bar), gets the listener there, so its press goes through `BeforeUserGlobalReload` as the screen's controls go through theirs. The Playlist Panel keeps an empty `UI/Canvas/Modules` the same way (issue #315), so its presses are checked too; having no dialog, it cannot say why one was refused. The Controller Bar has no such place, and so no permission check. Its buttons take presses beyond their icons, over 75 (the distance between them) through raycast padding, and its seek and volume bars over 40 and 50 of height (#318). A device learns its player only when one is chosen in its inspector (the KawaPlayer field of its `YamaPlayerSubController`), or when **GameObject > KawaPlayer** places it and can tell which: the nearest KawaPlayer it is placed inside, else the only one in its scene; with none or several, the field is left empty and the log says why (issue #267). Either way the player is written into the `UIController`, `YamaPlayerScreen` and `YamaPlayerSpeaker` under it (`YamaPlayerSubControllerEditor.LinkParts`). A device left without one (one dragged in from its prefab starts without), or a part added to it by a prefab update after the player was chosen, does nothing in the world: `DeviceLinkBuildProcess` names each such device in the build log, once, with what to do, and `UIController.Start` logs its path at run time (issue #294). The visitors app reads a `TabletVisitorRecorder` that keeps one record for the whole world: every tablet carries one, and `TabletVisitorsBuildProcess` keeps the first, moves it to the scene root, switches the others off and points every visitors app at it. The home button below the screen carries a white rounded square (`square.png`), and the LED around it (`led-ring.png`, a ring with its glow) lights while an app is open; on the home screen the LED is off and the button takes no press (`TabletScreen` switches the LED's object and the button's `interactable`; issue #180). A soft disc behind the LED shows where the button is pointed at. The project renders in linear colour space, where a faint alpha shows far stronger than in an image editor, so the glow's alpha in `led-ring.png` is stored raised to the power 1.7. The model's own button stands 0.6 mm proud of the bezel, so the button's UI sits 1 mm in front of the canvas (z = -6), or the model hides what is drawn inside the LED. The back carries the logo as a silver metal badge, 5 cm wide like a maker's mark, on a quad 0.3 mm off the body (`Body/Model/BackLogo`, `KawaTablet_Logo.mat`); the body's mobile shader has no transparency, so the logo uses the Standard shader in Fade mode. Unlike the matte body it is metallic and glossy, and a normal map (`KawaTablet_LogoNormal.png`, 256 x 256, crunched) gives it a chamfered edge, so it looks raised without more triangles and its edges catch the light. `Source~/logo_normal.py` makes the map from the logo; run it again when the logo changes.

The image app has two screens (issue #181): a list of the last five pictures shown, newest first, under the URL field, and the picture full size, with a back button that shows for a few seconds after the picture is touched and stays while a picture is loading or has failed. `TabletScreen` syncs the list (`VRCUrl[]`), the picture's URL and which screen is up, so late joiners see the same; the list lasts as long as the instance. A picture joins the list only when the download the entering player started succeeds, while that player still owns the screen and it is still the tablet's picture (synced URL), even if the list has been brought back up meanwhile: a late success, a retry or another player's download never writes over the shared state. Each player downloads only the picture that is up, never for the list, so a picture they have not loaded shows its site's name instead of a thumbnail. The download is copied into a `RenderTexture` no larger than 2048 (1024 on Quest) along its longest side and let go of at once; the last copy is freed before the next download starts, so only a picture being copied briefly shares memory with its copy. The RenderTextures have no depth buffer, which `VRCGraphics.Blit` needs on Quest. Thumbnails (at most 256 x 144, keeping the picture's shape) are made from that copy. A copy whose contents are lost is loaded again from its URL, and a lost thumbnail goes back to the site's name. A picture that has loaded can be shown on the KawaPlayer screen (issue #182): the button beside the back button sends it to the tablet's own `UIController` (`PlayImageUrl`), which plays it at once on the image viewer, without asking even over something playing, and through `BeforeUserPlayTrack`, so the permissions apply. The button shows only for a picture that has loaded, on a tablet pointed at a player.

When the image app cannot load a picture, it tells that player why and what to do next (issue #178). It sorts the failure by `VRCImageDownloadError` and by what VRChat's message adds: the HTTP status of a download error (`HTTP/1.1 403 Forbidden`: many sites refuse anything that is not a browser), a redirect, or an untrusted domain. It asks the player to turn on "Allow Untrusted URLs" only when that is the cause, and shows a "Try again" button only when trying again can help; the downloads are each player's own, so neither reaches anyone else. Unity's `Text` wraps only at spaces and knows no line-breaking rules, so the Japanese and Chinese texts of these messages carry their own line breaks and use no-break spaces around Latin words, each line short enough for the tablet.

The screen turns with the tablet (issue #183). Five times a second `TabletScreen` works out which side is up, and once the tablet has turned 55° past its last quarter turn, it turns the canvas's `Display` by that quarter and swaps its size between 1600 x 900 and 900 x 1600; lying flat changes nothing. Held upright, the apps take their portrait layout: each part in `TabletScreen._layoutParts` takes the anchors and rect stored for that orientation, and the layout groups in `_landscapeLayouts` are off, since they would put the parts back. So the home tiles stand two to a row, the settings categories become tabs along the top (placed by `SettingsPanel`, so a module's category is placed too), and the visitors app makes its rows from the portrait templates (`RowPortrait`), which take an extra line. To change a layout, select the tablet in the prefab and use **KawaPlayer > Tablet Layout**: Show Portrait, move the parts, Capture Portrait, then Show Landscape before saving; a part added to the list has to be captured in both. The KawaPlayer app is outside the canvas and stays landscape: held upright, it keeps its last landscape turn, and only upside down does it turn 180°. The scrolling views clip with `Mask`, not `RectMask2D`, which works out its rectangle from the root canvas and clips everything away once the display is turned; a mask's image must not be fully transparent (hide it with `showMaskGraphic` instead), or it clips everything too.

### Editor Tools (`Editor/`)

Custom inspectors, build processors, menu items, and the module/localization editors. Separate assembly (`Yamadev.YamaStream.Editor.asmdef`) referencing the runtime assembly. The header every KawaPlayer inspector draws (`EditorBase`: logo, version, language) has a button that opens the user guide on GitHub (`docs/guide` on develop), since the guide is not in the package; module inspectors, which hide the header, do not show it.

AVPro does not play in the editor unless **Debug > Enable AVPro Debug** (`Editor/VideoPlayer/AVProPlayerHelper.cs`) is used: it downloads AVPro's trial package and defines `AVPRO_DEBUG`, and `VideoPlayerResolver` then hands AVPro URLs to it. Otherwise a stand-in (`UnavailableAVProPlayer`) reports a player error, and the video falls back to Unity Video Player (issue #139). The editor assembly references AVPro's runtime assembly (`AVProVideo.Runtime`) by GUID, which is simply absent without AVPro. Up to 1.3.1 the package carried a sample of AVPro stand-in classes (`Samples~/AVProHelper`) and copied it into every project's `Assets/AVProVideo` when the editor opened; that sample and the copying are gone, and a copy left in a project does no harm.

`Editor/UdonSharp/UdonSharpProgramCheck.cs` repairs a state U# leaves when a project is opened without a Library (issue #265): U# compiles before the program assets are imported, binds none ("Compile of 0 scripts"), still records every script as compiled, and never compiles again, so the programs new in the version stay empty (Play: "Could not load the program") and the others keep the old code. Once per session and KawaPlayer version, after importing and U#'s own compile (its "U# Compile" progress item), or when Play is pressed first, it looks at KawaPlayer's programs without changing anything (never the `SerializedProgramAsset` getter, which creates, saves and refreshes assets) and, if one is missing, empty or lacks a field its script declares, runs `UdonSharpCompilerV1.CompileSync` once and checks again; still broken, it logs what to do and stops Play, and checks again on each Play without compiling. It is not a general check for old programs: one whose code alone changed is not found. The editor assembly references `VRC.Udon.Common.dll` for the program's types. The guide's "更新する" (`docs/guide/install.md`) shows the manual repair, Compile All UdonSharp Programs, with pictures.

## Key Constraints

- All runtime scripts must be valid UdonSharp (subset of C#). Many standard C# features are unavailable (no generics on UdonSharpBehaviour, limited reflection, no async/await, etc.).
- **`string → VRCUrl` conversion is impossible at runtime** (`new VRCUrl(string)` is editor-only). Any feature needing dynamic URLs must use the Pre-baked URL Pool pattern: a large `VRCUrl[]` of redirect-server slot URLs is baked into serialized fields at build time, and the server maps slots to real URLs via HTTP 302. See `docs/design/url-pool/README.md`.
- Network sync uses `[UdonSynced]` fields with manual sync (`UdonBehaviourSyncMode.Manual`). Only the owner can modify synced variables.
- **Never add an UdonBehaviour to, or remove one from, an object that already has one in a shipped prefab** (e.g. a second U# component beside the `Controller`). A world records the network components of each object when it is built; after the update the SDK reports "Network Components Changed" and refuses to build the world (`Failed to assign network IDs`) until its creator fixes it in the Network ID Utility. Put the new behaviour on a new child object, or into the existing one. ClientSim repairs this on Play, so only a world build shows it.
- **The U# code must compile on the oldest SDK the package accepts** (`vpmDependencies`: `com.vrchat.worlds` 3.10.2 and later, issue #193). A creator's project may stay on that SDK, since it satisfies the range, and Udon there can expose less than the SDK this project is developed on. The minimum was 3.8.1, inherited from upstream and never tried, until the tablet failed to compile there: Udon gained `Behaviour.enabled` only in 3.10.2 (issue #191). Call a Unity member through the concrete type where you can, and before relying on something newer, compile in a project with only the oldest SDK and KawaPlayer; to need a newer SDK, raise the minimum in `package.json`, this file and the README together.
- The project is primarily documented in Japanese. README and UI localization files contain Japanese as the primary language.

## Coding Style & Commits

- C# style follows upstream: 2-space indentation, braces on their own lines, `PascalCase` types/methods/properties, `_camelCase` private fields, namespaces under `Yamadev.YamaStream`.
- UnityEditor APIs belong only in `Editor/` or module editor assemblies; runtime assemblies must stay UdonSharp-safe.
- Preserve Unity `.meta` files when moving or adding assets.
- Commits use conventional-commit prefixes with optional scope: `fix:`, `feat:`, `docs(readme):`, etc. Keep subjects imperative.
