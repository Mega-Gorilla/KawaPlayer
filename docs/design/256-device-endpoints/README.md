## 要旨

KawaPlayer のデバイス（タブレット・ボタン・パネルなど）は、本体へのつなぎ方がデバイスごとに少しずつ違う。新しいデバイスを足すたびに、共通のインスペクターやビルド処理に手を入れている（#255）。

同じことを VizVid（VVMW）がどうしているかを比べると、VVMW は、つなぎ方を部品の欄で宣言し、ビルドで結んでいた。デバイスに固有の処理は部品の側に置かれ、前処理と本体のインスペクターは個別の部品を知らない（[comparison.md](comparison.md)）。

この文書は、KawaPlayer の接続口を、次の 4 つの考えで整理する方針を示す。

1. **正の値を 1 つにする：** どのプレイヤーに従うかを、デバイスの根元の 1 か所に持つ。
2. **デバイスのことはデバイスに置く：** デバイスの設定とビルドの処理を、デバイスの側に置く。
3. **接続口に名前を付ける：** 名前のイベントや UI の差し込み先に、一覧と名前を付ける。
4. **配る仕組みを 1 つの形にする：** イベントの配り先のリストを、同じ形にそろえる。

VVMW の土台のパッケージには依存せず、同じ考えを小さく自前で作ることをすすめる。今と整理したあとの違いは図 2 に、制作者から見える違いと更新したときの影響は表 7 にまとめた。決めることは 10 個（D1〜D10）あり、それぞれにおすすめを付けた。実装は子の issue 4 つに分け、見つかった不具合（AudioLink）と #206 の 2 つは先に直す。整理の入る版は、1.3.0 のあとをすすめる。

**キーワード：** デバイス、接続口、方針、正の値、ビルド時の処理、イベント、権限、VizVid

## 1. はじめに

### 1.1 背景

KawaPlayer の本体の横には、Controller Bar・Playlist Panel・Sub Screen・タブレット・全員リロードボタンの 5 種類のデバイスを置ける。タブレットや全員リロードボタンのように、これからもデバイスは増える。

#255 で今のつなぎ方を分析すると、次のことが分かった。

- つなぎ込みは、エディター・ビルド・実行時の 3 段に分かれている。
- 部品が「どのプレイヤーに従うか」を見つける方法が 3 通りある。
- タブレットの設定が、共通のインスペクターに入っている。
- 名前で呼ぶ接続口に一覧が無く、受け手が登録先を取り違えている所もあった（AudioLink）。

整理の論点は O1〜O8 として挙げた。#256 では、作りの成熟している VVMW と比べ（[comparison.md](comparison.md)）、そのうえで方針を決める。

### 1.2 目的

実装の前に、次の 3 つをまとめる。

1. KawaPlayer の問題と、その根拠と影響（§3）。
2. 問題ごとの直し方の案と、おすすめ（§4・§5）。
3. 確かめ方と進め方（§6・§7）。

この文書では実装しない。実装は、決めたことを子の issue に分けて行う（§7）。

### 1.3 読み方と、文書の分け方

- **この文書（方針）：** 何を直すか、どう直すかと、その理由を書く。決まったら、§5 に答えを書き込んで固める。
- **[comparison.md](comparison.md)（仕様と比較）：** KawaPlayer と VVMW が今どうつないでいるかを、機能ごとに並べた事実の記録。
- **[device-connections.md](../../analysis/device-connections.md)（現状の分析）：** KawaPlayer の接続口 E1〜E12 と論点 O1〜O8。この文書では、その番号を使う。

急ぐときは、§4.1（基本の方針と図 2）、§4.8（制作者から見える違い）、§5（決めること）、§7（進め方と表 11）を読めば足りる。

## 4. 直し方

### 4.1 基本の方針

![デバイスの根元の部品が、どのプレイヤーに従うかを持つ。ビルドのデバイスの処理が、それをもとに下の部品の参照を書き直して確かめる。デバイスのインスペクターの区画とビルドの処理はデバイスの側に置き、モジュールの UI は名前の付いた差し込み先に写す。イベントの名前は 1 つの一覧にまとめる](images/proposal.svg)

**図 1** 整理したあとのつなぎ方（案）。

![今は、エディターで選んだときだけ参照を書き、ビルドはデバイスごとに配線し、モジュールの UI をパスで写す。整理したあとは、置くときにプレイヤーを自動で選び、ビルドのデバイスの処理が正の値から参照を書き直して確かめ、モジュールの UI は名前の印に写す。実行時の登録は今のまま](images/before-after.svg)

**図 2** 今と、整理したあと（3 段ごと）。変わるのはエディターとビルドで、実行時の登録と、権限の確認の場所と、同期のしかたは変えない。

1. **正の値を 1 つにする（P1・P2）：**
   - **正の値：** デバイスの根元の `YamaPlayerSubController.YamaPlayer` を、どのプレイヤーに従うかの唯一の値にする。
   - **ビルド：** 下の部品の参照は、ビルドがこの値から書き直す。食い違いと未設定はログに出す。
   - **エディター：** インスペクターでの書き込みは、エディターですぐ見た目に出すためだけに残す。
2. **デバイスのことはデバイスに置く（P3・P4）：** デバイスのインスペクターの設定とビルドの処理を、デバイスの側に置く。共通のコード（Sub Controller のインスペクター、本体のビルド処理）は、個別のデバイスを知らない。
3. **接続口に名前を付ける（P5・P7・P8）：** 名前で呼ぶイベントと差し込み口に、1 つの一覧（定数）を作る。UI の差し込み先には、パスの代わりに名前を付ける。UI の中を外から読む所は、公開の窓口にする。
4. **配る仕組みを 1 つの形にする（P6）：** 配り先のリストの扱い（足す・配る）を共通の補助にそろえ、送り先と受け手の登録先の食い違いを無くす。
5. **VVMW の土台には依存しない（D1）：** vrcw-foundation の属性・前処理・基底クラスは使わず、上の考えを KawaPlayer の中で小さく作る。理由は §5 の D1。
6. **守ること：**
   - **Network ID：** 出荷済みのプレハブで、U# の部品がすでにある物に、U# の部品を足したり外したりしない。足す物は、子の物に置くか、ビルドで消える U# でない部品にする。
   - **SDK の下限：** U# は、最低の SDK（3.10.2）でコンパイルできるようにする。
   - **互換の方針：** 互換のためだけのコードは残さない。ただし、既存のプロジェクトを新しい版に更新したあとの動きは確かめ、移行が要るなら手順を案内する（CLAUDE.md の Compatibility & Technical Debt Policy）。

### 4.3 デバイスのことはデバイスに置く（P3・P4）

- **インスペクターの区画（D4）：** Sub Controller のインスペクターは、根元の下の部品の型を見て、その型に「区画」を登録したエディターのクラスがあれば、その区画を描く。
  - 例：タブレットの戻す設定と訪問者の顔写真を、タブレットの区画に移す。#206 の案内も、その区画に入る。
  - 共通のインスペクターに残すのは、色の組・言語・待ち受け画像・プレイヤーの欄のように、どのデバイスにもある物だけにする。
  - VVMW の Core のインスペクターが、操作する部品の設定を埋め込むのと同じ考えで、登録はエディターの属性で行う。
  - **小さく始める：** まずタブレットの区画の移動だけを作る。区画を登録する属性は 1 つに留め、VVMW の `[Locatable]`・`[Resolve]` のような汎用の属性の仕組みは作らない。
- **ビルドの処理：**
  - デバイスに固有のビルド処理は、デバイスの側のフォルダーに置く。今のタブレットの訪問者の記録の処理は、共通の `Editor/Build/` にある。
  - 「デバイスがどのプレイヤーに従うか」を、共通の補助として用意する。タブレットと全員リロードボタンは、それを使う。
  - 「ワールドに 1 つだけ残す」は、使うのがタブレットの訪問者の記録だけなので、共通の仕組み（VVMW の `ISingleton` のような物）は作らず、今の専用の処理をタブレットの側に移すだけにする。2 つ目が要るようになったら、共通にする。

### 4.4 名前の一覧と、配る仕組み（P5・P6・P8）

**表 4** イベントの選択肢

| 案 | 中身 | 良いところ | 気になるところ |
| --- | --- | --- | --- |
| **A（おすすめ）** | 名前のイベントを 1 つの static クラスの定数にまとめ、送る側はそれを使う。配り先のリストの「足す・配る」は、共通の補助（今の `ArrayUtils.Add` と同じ形）にそろえる。受け手の登録先と送り先の食い違い（AudioLink）を直す。名前と受け手のメソッドが合っているかを、エディターのテストで確かめる。差し込み口（E7）は、VVMW の `InputFilterBase` のように、抽象の基底クラスで型付きにする | 今の作り（実行時の `AddListener`）のまま、名前の取り違えを減らせる。U# の制約に合う（static クラスの定数と拡張メソッドは、今も U# から使っている） | 受け手のメソッドの名前は、コンパイルでは確かめられない（テストで補う） |
| B | VVMW のように、共通の基底クラスと、ビルドでの購読（属性）を作る | 配り先がインスペクターとビルドで見える。受ける名前をビルドで絞れる | 送り手の基底を、`YamaPlayerBehaviour`・`YamaPlayerListener` の継承の中に組み込むことはできるが、すべての U# の部品の基底が組み変わり、影響が大きい。配り先を保存する欄が増え、U# のプログラムのアセットとプレハブの差分も大きい。今の困りごとには要らない |
| C | 今のまま | 手間が無い | P5・P6 が残る |

- **型付きの差し込み口：** VVMW の `InputFilterBase`（[comparison.md](comparison.md) §8.3）と同じく、コアに抽象の基底クラス（例：URL を受け取り、引き受けたかを返す）を置き、`UIController._urlInterceptor` をその型にする。`PlaylistLoaderUI` はそれを継ぐ。U# の継承は 1 本なので、基底クラスは `YamaPlayerListener` を継いでおく（`PlaylistLoaderUI` は今も `YamaPlayerListener` を継ぐ）。プレイリストの更新（`_playlistRefreshHandler`）も同じ形にし、URL の受け付けと更新を 1 つの継承の中で持つ。子の issue では、次の 3 つを保つことを具体にする。
  - 引き受けたかどうかは、呼んだその場で返す（今の `interceptHandled` と同じ）。
  - どの UI から呼ばれたかを受け取る（今の `interceptSource`）。結果の案内は、その UI に出す。
  - 読み込みの結果は、今と同じくあとから届く（非同期）。
- **UI の中を読む所（P8）：** `SlideShowerUI` が読む時刻の文字と進み具合のスライダーは、`UIController` に公開の窓口を足して、そこから書く。`ProgressHeld` はもうある。
- **AudioLink（P6）：** コードからは不具合と読めるので、方針を待たずに別の issue で、まず再現を確かめてから直すことをすすめる（D10）。

### 4.5 UI の差し込み先に名前を付ける（P7）

**表 5** 差し込み先の選択肢

| 案 | 中身 | 良いところ | 気になるところ |
| --- | --- | --- | --- |
| **A（おすすめ）** | UI のプレハブの差し込み先に、名前を持つ印の部品（U# でない、ビルドで消える部品）を置く。モジュールの `uiSlots` は、パスの代わりに名前で写す先を指す。どの UI にも写されなかったモジュールの UI は、ビルドのログに出す | UI の作りを変えても外れない。デバイスは、受け付ける差し込み先を印で示せばよい | KawaPlayer の UI とモジュールのプレハブを、すべて書き直す。外の人が作ったモジュール（今は知られていない）は、名前に書き直す必要がある |
| B | パスのまま、どの UI にも写されなかったときにログに出す | 手間が小さい | UI の作りに縛られたまま |
| C | 今のまま | 手間が無い | P7 が残る |

印の部品は U# でないので、Network ID には関わらない見込みである。これは、子の issue の最初に、SDK のビルドで確かめる。

- **小さく始める：** まず、実在する差し込み先に名前を付けることと、名前の重複の検出だけを作る。
- **欠けに気づける：** 権限のリスナーのように、写されないと権限がかからなくなる物がある。差し込み先が無くて写されなかった UI を、ログで分かるようにする（今は、Controller Bar と Playlist Panel が、合うパスが無くて権限のリスナーを受けない）。

### 4.6 権限と、命令の入り口（P9）

**表 6** 権限の選択肢

| 案 | 中身 | 良いところ | 気になるところ |
| --- | --- | --- | --- |
| **A（おすすめ）** | 今の UI 側の確認（前の確認 E5）を残し、境目を決まりとして文書に書く（下の 2 つ） | KawaPlayer の細かい権限（26 個の操作、全員で共有）を残せる。今のデバイスとモジュールは、どれもこの境目を守っている | 決まりを破るコードは、レビューでしか止められない |
| B | VVMW のように、受ける側（`Controller`）で権限を確かめる | どこから呼んでも同じになる | `Controller` が、利用者の操作と中の処理（自動再生・リトライなど）を見分ける必要があり、手間と危険が大きい。VVMW も、受ける側で断るのは 5 つの命令だけ |

案 A の境目は、次のとおりである。

1. **利用者が始める、共有の操作：** その入口の `UIController` で、対応する `BeforeUserXxx` を通す。全員リロードボタンのように、`UIController` で確かめてからモジュールを呼ぶ入口も、これに当たる。
2. **中の処理：** 確かめたあとの実行、ネットワークの受信、自動再生、復元、リトライなどは、`Controller` やモジュールを直接呼んでよい。今も、次のものが直接呼んでいる。
   - 自動再生：`AutoPlay`・`DefaultUrlController`
   - 全員リロードの受け手：`GlobalReload.OnGlobalReload`
   - スライドショー：`SlideShower`
   - 設定の復元：`Persistence`

   これらを `UIController` に寄せると、自動再生のために UI を選ぶ依存が増え、権限と所有権の扱いも変わる。整理の目的（振る舞いを変えない）に反する。

Controller Bar と Playlist Panel に権限の UI が無い（権限がかからない）ことは、今のまま残す。変えるなら、別に決める。

### 4.7 取り入れないもの

- **VVMW の土台への依存：** §5 の D1。
- **ビルドでのイベントの購読（属性）：** 表 4 の B。今の実行時の登録で困っていない。
- **持てる・戻す・同期の作りの統一（P10）：** 持てるデバイスは今 2 つで、作りの違いが困りごとになっていない。3 つ目の持てるデバイスを足すときに見直す。
- **複数のプレイヤーの切り替え（VVMW の `ActiveRegionManager`）：** KawaPlayer のデバイスは、1 台のプレイヤーに従う作りで足りている。

## 8. まとめ
