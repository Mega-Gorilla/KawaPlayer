## 要旨

KawaPlayer のデバイス（タブレット・ボタン・パネルなど）は、利用者の操作を、それぞれが持つ `UIController` で確かめてから、本体を直接呼んでいる。権限を確かめる部品は、UI ごとに写している。そのため、写す場所の無い Controller Bar と Playlist Panel には権限がかからない。モジュールの UI には、確認を通らずに全員の設定を変える物もある（#211）。新しいデバイスを足すたびに、確かめる部品の置き場所と、本体へのつなぎ方を用意し直している（#255）。

VizVid（VVMW）は、再生とプレイリストの命令を、本体ごとに 1 つの `FrontendHandler` で受けていた（[comparison.md](comparison.md) §8.4）。

この文書は、KawaPlayer の接続口を、**プレイヤーごとに 1 つの窓口**を中心に組み直す方針を示す。

1. **窓口を 1 つにする：** 利用者の操作の確認と、本体やモジュールを変える命令を、プレイヤーごとに 1 つの窓口で受ける。デバイスと UI は、命令を窓口にだけ出す。権限は、窓口で確かめる。
2. **正の値を 1 つにする：** デバイスがどのプレイヤーの窓口に従うかを、デバイスの根元の 1 か所に持ち、ビルドで下の部品にそろえる。
3. **デバイスのことはデバイスに置く：** デバイスの設定とビルドの処理を、デバイスの側に置く。
4. **接続口に名前を付ける：** 確認のイベント・名前の出来事・UI の差し込み先に、一覧と名前を付ける。

値を読むこと（再生位置など）と出来事（`AfterXxx`）は、今のまま本体から受ける。自動再生などの中の処理も、今のまま本体を直接呼ぶ。窓口が受け持つのは、利用者の操作の入口だけである。

窓口の流れは図 3 に、今と組み直したあとの違いは図 2 に、制作者から見える違いと更新したときの影響は表 8 にまとめた。決めることは 13 個（D1〜D13）ある。実装は子の issue 6 つに分け、窓口を最初に作る。見つかった不具合（AudioLink）と #206 は先に直す。組み直しの入る版は、1.3.0 のあとをすすめる。

**キーワード：** デバイス、接続口、窓口、権限、正の値、ビルド時の処理、イベント、VizVid

## 1. はじめに

### 1.1 背景

KawaPlayer の本体の横には、Controller Bar・Playlist Panel・Sub Screen・タブレット・全員リロードボタンの 5 種類のデバイスを置ける。タブレットや全員リロードボタンのように、これからもデバイスは増える。

#255 で今のつなぎ方を分析すると、次のことが分かった。

- つなぎ込みは、エディター・ビルド・実行時の 3 段に分かれている。
- 部品が「どのプレイヤーに従うか」を見つける方法が 3 通りある。
- タブレットの設定が、共通のインスペクターに入っている。
- 名前で呼ぶ接続口に一覧が無く、受け手が登録先を取り違えている所もあった（AudioLink）。
- 利用者の操作は、デバイスごとの `UIController` が確かめて、本体を直接呼ぶ。権限を確かめる部品は、UI ごとに写す。

整理の論点は O1〜O8 として挙げた。#256 では、作りの成熟している VVMW と比べ（[comparison.md](comparison.md)）、そのうえで方針を決める。

#256 の最初の案（2026-10-16）は、今の作りのまま「利用者の操作は UI で確かめる」を決まりとして書くものだった。その案はレビューを通ったが、デバイスが増えても問題が起きにくいように、VVMW の `FrontendHandler` のような窓口を置き、問い合わせ先を 1 つにする方針に変えた（2026-10-16 決定）。この文書は、その方針で組み直したものである。

### 1.2 目的

実装の前に、次の 3 つをまとめる。

1. KawaPlayer の問題と、その根拠と影響（§3）。
2. 問題ごとの直し方の案と、おすすめ（§4・§5）。
3. 確かめ方と進め方（§6・§7）。

この文書では実装しない。実装は、決めたことを子の issue に分けて行う（§7）。

### 1.3 読み方と、文書の分け方

- **この文書（方針）：** 何を直すか、どう直すかと、その理由を書く。決まったら、§5 に答えを書き込んで固める。
- **[comparison.md](comparison.md)（仕様と比較）：** KawaPlayer と VVMW が今どうつないでいるかを、機能ごとに並べた事実の記録。
- **[device-connections.md](../../analysis/device-connections.md)（現状の分析）：** KawaPlayer の接続口 E1〜E12 と論点 O1〜O8。この文書では、その番号を使う。

急ぐときは、§4.1（基本の方針と図 1・図 2）、§4.2（窓口と図 3）、§4.8（制作者から見える違い）、§5（決めること）、§7（進め方）を読めば足りる。

## 4. 直し方

### 4.1 基本の方針

![デバイスと UI は、命令をプレイヤーごとに 1 つの窓口に出す。窓口は確認のイベントを配り、権限が通せば本体やモジュールを呼ぶ。権限は窓口に 1 回だけ登録する。自動再生などの中の処理は、窓口を通らずに本体を呼ぶ。値を読むことと出来事を受けることは、今のまま本体から。下に、正の値と足し方、デバイスのことはデバイスに、名前を付ける、の 3 つを並べる](images/proposal.svg)

**図 1** 組み直したあとのつなぎ方（案）。

![今は、エディターで選んだときだけ参照を書き、ビルドはデバイスごとに配線し、実行時は UI ごとに確かめて本体を直接呼ぶ。組み直したあとは、置くときにプレイヤーを自動で選び、ビルドのデバイスの処理が窓口の参照をそろえ、実行時の命令は窓口を通る。値の読み方と出来事の受け方は今のまま](images/before-after.svg)

**図 2** 今と、組み直したあと（3 段ごと）。エディターとビルドに加えて、実行時の命令の道が変わる。値の読み方と出来事の受け方、中の処理の呼び方、同期のしかたは変えない。

1. **窓口を 1 つにする（P1・P2・P3）：** プレイヤーごとに 1 つの窓口を置き、利用者の操作の確認と、本体やモジュールを変える命令をそこで受ける。デバイス・UI・モジュールの UI は、命令を窓口にだけ出す。権限は窓口に 1 回だけ登録する（§4.2）。
2. **正の値を 1 つにする（P4・P5）：**
   - **正の値：** デバイスの根元の `YamaPlayerSubController.YamaPlayer` を、どのプレイヤーに従うかの唯一の値にする。
   - **ビルド：** 下の部品が持つ窓口と本体の参照は、ビルドがこの値から書き直す。食い違いと未設定はログに出す。
   - **エディター：** インスペクターでの書き込みは、エディターですぐ見た目に出すためだけに残す。
3. **デバイスのことはデバイスに置く（P6・P7）：** デバイスのインスペクターの設定とビルドの処理を、デバイスの側に置く。共通のコード（Sub Controller のインスペクター、本体のビルド処理）は、個別のデバイスを知らない。
4. **接続口に名前を付ける（P8・P9・P10・P11）：** 確認のイベントと名前の出来事に、1 つの一覧（定数）を作り、配り先のリストの扱いをそろえる。UI の差し込み先には、パスの代わりに名前を付ける。UI の中を外から読む所は、公開のメソッドにする。
5. **VVMW の土台には依存しない（D11）：** vrcw-foundation の属性・前処理・基底クラスは使わず、上の考えを KawaPlayer の中で小さく作る。
6. **守ること：**
   - **Network ID：** 出荷済みのプレハブで、U# の部品がすでにある物に、U# の部品を足したり外したりしない。窓口は、新しい子の物に置く。足すほかの物は、子の物に置くか、ビルドで消える U# でない部品にする。
   - **SDK の下限：** U# は、最低の SDK（3.10.2）でコンパイルできるようにする。
   - **互換の方針：** 互換のためだけのコードは残さない。ただし、既存のプロジェクトを新しい版に更新したあとの動きは確かめ、移行が要るなら手順を案内する（CLAUDE.md の Compatibility & Technical Debt Policy）。

### 4.2 窓口（P1・P2・P3）

- **置き場所：** 本体のプレハブ（`KawaPlayer.prefab`）に、新しい子の物として 1 つ置く（名前は仮に `PlayerFrontend`）。窓口は何も同期しない。
- **持つ物：** 本体（`Controller`）とモジュールへの参照、確認のイベントの配り先、URL の差し込み口。

**表 3** 窓口が受け持つ範囲の選択肢

| 案 | 中身 | 良いところ | 気になるところ |
| --- | --- | --- | --- |
| **A（おすすめ）** | 利用者の操作の確認（26 種類すべて）と、本体・モジュールを変える命令の実行を受け持つ。値を読むことと出来事は、今のまま本体から受ける | 命令は窓口の中で確かめてから動くので、確認を飛ばせない。中継するのは操作のときだけなので、重さは変わらない | `UIController` が本体を変える 62 か所（所有権を取る 25 か所を含む）を書き換える |
| B | A に加え、値を読むことと出来事も窓口が中継する | 問い合わせ先が完全に 1 つになる | UI が毎フレーム読む値まで中継するので、部品をまたぐ呼び出し（Udon では重い）が UI の数だけ増える。機能を足すたびに窓口を書き換える |
| C | 確認だけを窓口に集め、命令は今のまま UI が本体を呼ぶ | 手間が小さい | 確認を飛ばして本体を呼ぶ道が残り、決まりでしか止められない（P3 が残る） |

**表 4** 窓口が受ける物と、受けない物（案 A）

| 区分 | 中身 | どこで扱うか |
| --- | --- | --- |
| 受ける | 利用者の操作の確認（`BeforeUserXxx`、26 種類）。権限のモジュールは、窓口に 1 回だけ登録する | 窓口 |
| 受ける | 本体を変える命令（再生・一時停止・停止・シーク・URL・リストから選ぶ・キュー・リピート・シャッフル・速度・プレーヤーの切り替え・音量など。今 `UIController` が呼ぶ命令 17 種類と設定の書き込み 10 種類）。所有権を取る処理（`TakeOwnership`）も窓口に移る | 窓口が確かめてから本体を呼ぶ |
| 受ける | モジュールの、全員に届く操作の確認（全員リロード・音程・スライドショー・自動再生(Owner) の URL） | 窓口が確かめ、通ればモジュールの UI がモジュールを呼ぶ |
| 受ける | URL の差し込み口（E7、型付き。§4.5） | 窓口に 1 つ |
| 受ける | 断ったときの知らせ（D2） | 窓口が出す |
| 受けない | 値を読むこと（再生位置・状態・曲名など） | 今のまま本体から |
| 受けない | 出来事（`AfterXxx`・名前の出来事） | 今のまま本体に登録して受ける |
| 受けない | 中の処理（自動再生・全員リロードの受信・設定の復元・リトライ） | 今のまま本体を直接呼ぶ |
| 受けない | UI だけの仕事（表示・翻訳・ダイアログ） | 今のまま `UIController` |
| 受けない | デバイスが自分だけで持つ同期（タブレットの画像アプリの画面と一覧） | 今のままデバイス。権限は通らない |

![UI やデバイスが、自分を添えて窓口の命令を呼ぶ。窓口が確認のイベントを権限に配り、断られたら呼んだ物に知らせ、通れば本体を呼ぶ。本体の出来事は今のまま UI に届く。モジュールの UI は、窓口に確かめてもらってから、自分のモジュールを呼ぶ](images/gateway.svg)

**図 3** 窓口が操作を受けて流すまで（案 A）。

- **流れ：**
  1. UI やデバイスが、自分を添えて窓口の命令を呼ぶ。
  2. 窓口が確認のイベントを配る。権限のモジュールは、足りなければ断る。
  3. 断られたら、窓口が知らせを出す（D2）。通れば、窓口が本体を呼ぶ。
- **モジュールの操作：** 本体の側（コア）は、モジュールの型を知らない。そこでモジュールの UI は、窓口に確認だけを頼み、通ったら自分のモジュールを呼ぶ。今の全員リロードボタンと同じ形である。
- **モジュールに固有の決まり：** 「自動再生(Owner) の URL を変えられるのはインスタンスのオーナーだけ」のような決まりは、モジュールに残す。権限のモジュールがどの確認に答えるかは、今と同じく権限のモジュールが決める。自動再生(Owner) の URL を変える確認には答えず、今と同じくモジュールの決まりだけで確かめる。
- **聞くだけの口：** 全員リロードボタンは、押せるかを 1 秒ごとに聞き、押せなければ NO ACCESS を出す。窓口には、知らせを出さずに聞くだけの口も置く。
- **中止の旗：** 今の `UIController` は、1 つの旗（`_actionCancelled`）で中止を伝えるので、確認の中で別の確認を送れない（URL の差し込み口が専用の欄なのは、このため）。窓口でも同じ制約を守り、URL の差し込み口は確認より前に呼ぶ。
- **守らせ方：** デバイスと UI が設定で持つのは、窓口への参照だけにする（D5）。本体の参照は、値を読むためと出来事に登録するために、窓口から受け取る。UI・デバイス・モジュールの UI のコードが本体の命令を直接呼んでいないかを、エディターのテストで確かめる。
- **断ったときの知らせ（D2）：** 呼んだ UI にダイアログがあれば、そこに出す。Controller Bar・Playlist Panel・全員リロードボタンにはダイアログが無いので、本体のスクリーンに出す。全員リロードボタンは、今の NO ACCESS の表示も残す。
- **Controller Bar と Playlist Panel（D3）：** 窓口を通るので、権限がかかるようになる。今かからないのは、確かめる部品を写す場所が無いために起きている漏れである。
- **音程とスライドショーの設定（D4、#211）：** 窓口の確認を通すように直し、権限のモジュールはその確認に答える（Editor 以上）。確認のイベントは、モジュールの操作の分だけ 26 種類に足す（名前は子の issue で決める。図 3 の `BeforeUserChangePitch` は例）。#211 は、窓口を作る子の issue 1 の中で直す。先に `UIController` に確認を足すと、窓口のときにもう一度移すことになる。

### 4.4 デバイスのことはデバイスに置く（P6・P7）

- **インスペクターの区画（D8）：** Sub Controller のインスペクターは、根元の下の部品の型を見て、その型に「区画」を登録したエディターのクラスがあれば、その区画を描く。
  - 例：タブレットの戻す設定と訪問者の顔写真を、タブレットの区画に移す。#206 の案内も、その区画に入る。
  - 共通のインスペクターに残すのは、色の組・言語・待ち受け画像・プレイヤーの欄のように、どのデバイスにもある物だけにする。
  - VVMW の Core のインスペクターが、操作する部品の設定を埋め込むのと同じ考えで、登録はエディターの属性で行う。
  - **小さく始める：** まずタブレットの区画の移動だけを作る。区画を登録する属性は 1 つに留め、VVMW の `[Locatable]`・`[Resolve]` のような汎用の属性の仕組みは作らない。
- **ビルドの処理：**
  - デバイスに固有のビルド処理は、デバイスの側のフォルダーに置く。今のタブレットの訪問者の記録の処理は、共通の `Editor/Build/` にある。
  - 「デバイスがどのプレイヤーに従うか」を、共通の補助として用意する。タブレットと全員リロードボタンは、それを使う。
  - 「ワールドに 1 つだけ残す」は、使うのがタブレットの訪問者の記録だけなので、共通の仕組み（VVMW の `ISingleton` のような物）は作らず、今の専用の処理をタブレットの側に移すだけにする。2 つ目が要るようになったら、共通にする。
- **全員リロードボタン：** 権限を聞くためだけに持っていた `UIController` と空の `Canvas/Modules` は、窓口のあとは要らなくなる見込みである。外すかは、色や翻訳に使っていないかを確かめて、子の issue で決める。

### 4.7 取り入れないもの

- **VVMW の土台への依存：** §5 の D11。
- **プレイリストとキューを窓口に移すこと：** VVMW の `FrontendHandler` はプレイリストとキューを持つが、KawaPlayer では本体（`Controller`・`QueueList`・`HistoryList`）が持って同期している。移すと同期の作りが変わる。窓口が受け持つのは、利用者の操作の入口だけにする。
- **値を読むことと出来事の中継：** 表 3 の B。
- **受ける側（本体）で権限を確かめること：** VVMW の `FrontendHandler` は、受けた命令のうち 5 つをロックで断る。KawaPlayer の本体は、利用者の操作と中の処理（自動再生・リトライなど）を見分けられない。窓口には利用者の操作だけが来るので、見分けが要らない。
- **ビルドでのイベントの購読（属性）：** 表 6 の B。今の実行時の登録で困っていない。
- **持てる・戻す・同期の作りの統一（P12）：** 持てるデバイスは今 2 つで、作りの違いが困りごとになっていない。3 つ目の持てるデバイスを足すときに見直す。
- **複数のプレイヤーの切り替え（VVMW の `ActiveRegionManager`）：** KawaPlayer のデバイスは、1 台のプレイヤーに従う作りで足りている。

## 8. まとめ

- **中心：** プレイヤーごとに 1 つの窓口を置き、利用者の操作の確認と命令をそこに集める。デバイスと UI は、命令を窓口にだけ出す。権限は窓口で 1 回だけ確かめるので、デバイスを足しても権限が漏れない。
- **ほかの 3 つの考え：** 「正の値を 1 つ」「デバイスのことはデバイスに」「接続口に名前」。
- **VVMW から取り入れる物：** `FrontendHandler` のように受け口を本体ごとに 1 つにする考え（VVMW より広く、利用者の操作をすべて通す）、つなぎ方を部品の側で決める考え、置くときに結ぶ考え。土台のパッケージには依存しない。
- **残す物：** KawaPlayer の細かい権限（26 種類の確認、全員で共有）、値の読み方と出来事の受け方、中の処理の呼び方、プレイリストとキューの持ち場、同期のしかた。
- **進め方：** 決めることは 13 個（D1〜D13）。実装は子の issue 6 つと、先に直す 2 つに分ける。
