## 要旨

KawaPlayer のデバイス（タブレット・ボタン・パネルなど）は、利用者の操作を、それぞれが持つ `UIController` で確かめてから、本体を直接呼んでいる。この作りには、次の問題がある。

- **権限の部品の写し：** 権限を確かめる部品は、UI ごとに写している。写す場所の無い Controller Bar と Playlist Panel には、権限がかからない。
- **確認と置き換えの混在：** 確認のイベントは、権限の確認と、別の機能による操作の置き換え（スライドショー）を兼ねている。登録の順番によっては、権限を見る前にスライドが動く。
- **確認を通らない UI：** モジュールの UI には、確認を通らずに全員の設定を変える物もある（#211）。
- **デバイスごとの用意：** 新しいデバイスを足すたびに、確かめる部品の置き場所と、本体へのつなぎ方を用意し直している（#255）。

VizVid（VVMW）は、再生とプレイリストの命令を、本体ごとに 1 つの `FrontendHandler` で受けていた（[comparison.md](comparison.md) §8.4）。

この文書は、KawaPlayer の接続口を、**プレイヤーごとに 1 つの窓口**を中心に組み直す方針を示す。窓口は、今の確認のイベントを移す場所ではない。**権限の判断と操作の受付を分けた、利用者の操作の層**である。

1. **窓口を 1 つにする：** 利用者の操作は、プレイヤーごとに 1 つの窓口が、受付 → 権限の判断 → 振り分け → 実行の順に流し、結果を返す。
   - **権限の判断：** UI から切り離し、副作用を持たない。
   - **照会と実行：** 聞くだけの照会と、実行の前の確認を分ける。
   - **表示：** 窓口は表示をせず、結果をどう見せるかは、呼んだデバイスが決める。
   - **モジュール：** 窓口に処理を登録し、窓口はモジュールの型を知らない。
2. **正の値を 1 つにする：** デバイスがどのプレイヤーの窓口に従うかを、デバイスの根元の 1 か所に持ち、ビルドで下の部品にそろえる。
3. **デバイスのことはデバイスに置く：** デバイスの設定とビルドの処理を、デバイスの側に置く。
4. **接続口に名前を付ける：** 操作の種類・名前の出来事・UI の差し込み先に、一覧と名前を付ける。

値を読むこと（再生位置など）と出来事（`AfterXxx`）は、今のまま本体から受ける。自動再生などの中の処理も、今のまま本体を直接呼ぶ。窓口を置くだけでは本体を直接呼ぶ道は塞がらないので、デバイスが本体の状態を変えていないかを、エディターの検査で見つける。

窓口の流れは図 3 に、今と組み直したあとの違いは図 2 に、制作者から見える違いと更新したときの影響は表 9 にまとめた。決めることは 13 個（D1〜D13）ある。

実装は、子の issue 8 つに分ける。

- **最初の 2 つ：** 権限の判断を UI から切り離し、一時停止だけを窓口に通して確かめる。
- **そのあと：** 操作をまとまりごとに移す。
- **挙動が変わる直し：** 権限の漏れを直す所（Controller Bar・Playlist Panel、スライドショー、#211）は、挙動の変更として明示する。
- **先に直すもの：** 見つかった不具合（AudioLink）と #206 は先に直す。

組み直しの入る版は、1.3.0 のあとをすすめる。

## 1. はじめに

### 1.1 背景

KawaPlayer の本体の横には、Controller Bar・Playlist Panel・Sub Screen・タブレット・全員リロードボタンの 5 種類のデバイスを置ける。タブレットや全員リロードボタンのように、これからもデバイスは増える。

#255 で今のつなぎ方を分析すると、次のことが分かった。

- つなぎ込みは、エディター・ビルド・実行時の 3 段に分かれている。
- 部品が「どのプレイヤーに従うか」を見つける方法が 3 通りある。
- タブレットの設定が、共通のインスペクターに入っている。
- 名前で呼ぶ接続口に一覧が無く、受け手が登録先を取り違えている所もあった（AudioLink）。
- 利用者の操作は、デバイスごとの `UIController` が確かめて、本体を直接呼ぶ。権限を確かめる部品は、UI ごとに写す。

整理の論点は O1〜O8 として挙げた。#256 では、作りの成熟している VVMW と比べ（[comparison.md](comparison.md)）、そのうえで方針を決める。

#256 の最初の案（2026-10-16）は、今の作りのまま「利用者の操作は UI で確かめる」を決まりとして書くものだった。その案はレビューを通った。しかし、デバイスが増えても問題が起きにくいように、VVMW の `FrontendHandler` のような窓口を置き、問い合わせ先を 1 つにする方針に変えた（2026-10-16 決定）。

さらに、実装についてのレビューの意見（2026-10-16）を受け、窓口を「今の確認のイベントを移す場所」ではなく、「権限の判断と操作の受付を分けた、利用者の操作の層」として設計した。この文書は、その方針で組み直したものである。

### 1.2 目的

実装の前に、次の 3 つをまとめる。

1. KawaPlayer の問題と、その根拠と影響（§3）。
2. 問題ごとの直し方の案と、おすすめ（§4・§5）。
3. 確かめ方と進め方（§6・§7）。

この文書では実装しない。実装は、決めたことを子の issue に分けて行う（§7）。

### 1.3 読み方と、文書の分け方

- **この文書（方針）：** 何を直すか、どう直すかと、その理由を書く。決まったら、§5 に答えを書き込んで固める。
- **[comparison.md](comparison.md)（仕様と比較）：** KawaPlayer と VVMW が今どうつないでいるかを、機能ごとに並べた事実の記録。
- **[device-connections.md](../../analysis/device-connections.md)（現状の分析）：** KawaPlayer の接続口 E1〜E12 と論点 O1〜O8。この文書では、その番号を使う。

急ぐときは、§4.1（基本の方針と図 1・図 2）、§4.2（窓口と図 3）、§4.8（制作者から見える違い）、§5（決めること）、§7（進め方）を読めば足りる。

## 4. 直し方

### 4.1 基本の方針

![デバイスと UI は、操作をプレイヤーごとに 1 つの窓口に出す。窓口は、受付、権限の判断、振り分け、実行の順に流し、結果を返す。表示はデバイスが決める。権限の判断とスライドショーなどの引き受け手は、モジュールが窓口に登録する。自動再生などの中の処理は、窓口を通らずに本体を呼ぶ。値を読むことと出来事を受けることは、今のまま本体から。下に、正の値と足し方、デバイスのことはデバイスに、名前を付ける、の 3 つを並べる](images/proposal.svg)

**図 1** 組み直したあとのつなぎ方（案）。

![今は、エディターで選んだときだけ参照を書き、ビルドはデバイスごとに配線して権限の部品を UI ごとに写し、実行時は UI ごとに確かめて本体を直接呼ぶ。組み直したあとは、置くときにプレイヤーを自動で選び、ビルドのデバイスの処理が窓口の参照をそろえ、実行時の操作は窓口が判断・振り分け・実行して結果を返す。値の読み方と出来事の受け方は今のまま](images/before-after.svg)

**図 2** 今と、組み直したあと（3 段ごと）。エディターとビルドに加えて、実行時の操作の道が変わる。値の読み方と出来事の受け方、中の処理の呼び方、同期のしかたは変えない。

1. **窓口を 1 つにする（P1〜P5）：** プレイヤーごとに 1 つの窓口を置き、利用者の操作を、受付 → 権限の判断 → 振り分け → 実行の順に流す。権限の判断は UI から切り離し、モジュールは判断と引き受け手を窓口に登録する（§4.2）。
2. **正の値を 1 つにする（P6・P7）：**
   - **正の値：** デバイスの根元の `YamaPlayerSubController.YamaPlayer` を、どのプレイヤーに従うかの唯一の値にする。
   - **ビルド：** 下の部品が持つ窓口と本体の参照は、ビルドがこの値から書き直す。食い違いと未設定はログに出す。
   - **エディター：** インスペクターでの書き込みは、エディターですぐ見た目に出すためだけに残す。
3. **デバイスのことはデバイスに置く（P8・P9）：** デバイスのインスペクターの設定とビルドの処理を、デバイスの側に置く。共通のコード（Sub Controller のインスペクター、本体のビルド処理）は、個別のデバイスを知らない。
4. **接続口に名前を付ける（P10〜P13）：** 操作の種類と名前の出来事に、1 つの一覧（定数）を作り、配り先のリストの扱いをそろえる。UI の差し込み先には、パスの代わりに名前を付ける。UI の中を外から読む所は、公開のメソッドにする。
5. **VVMW の土台には依存しない（D11）：** vrcw-foundation の属性・前処理・基底クラスは使わず、上の考えを KawaPlayer の中で小さく作る。
6. **守ること：**
   - **Network ID：** 出荷済みのプレハブで、U# の部品がすでにある物に、U# の部品を足したり外したりしない。窓口は、新しい子の物に置く。足すほかの物は、子の物に置くか、ビルドで消える U# でない部品にする。
   - **SDK の下限：** U# は、最低の SDK（3.10.2）でコンパイルできるようにする。
   - **互換の方針：** 互換のためだけのコードは残さない。ただし、既存のプロジェクトを新しい版に更新したあとの動きは確かめ、移行が要るなら手順を案内する（CLAUDE.md の Compatibility & Technical Debt Policy）。
   - **挙動の変更：** 権限の漏れを直す所（D3・D4、スライドショー）は、書き換えではなく挙動の変更として、PR とリリースノートに書く。

### 4.2 利用者の操作の層（窓口）（P1〜P5）

窓口は、今の確認のイベント（`BeforeUserXxx`）を移す場所ではない。権限の判断と、操作の受付・振り分けを分けた、利用者の操作の層として作る。

- **置き場所：** 本体のプレハブ（`KawaPlayer.prefab`）に、新しい子の物として 1 つ置く（名前は仮に `PlayerFrontend`）。窓口は何も同期しない。`UIController` の無いデバイス（小さなボタンなど）からも使える。
- **持つ物：** 本体（`Controller`）への参照と、モジュールが登録する物（権限の判断・操作の引き受け手・URL の差し込み口）。窓口（コア）は、モジュールの型を知らない。

**表 3** 窓口の形の選択肢

| 案 | 中身 | 良いところ | 気になるところ |
| --- | --- | --- | --- |
| **A（おすすめ）** | 利用者の操作の層。受付 → 権限の判断 → 振り分け → 実行の順に流し、結果を返す。権限の判断は UI から切り離し、副作用を持たない。聞くだけの照会と、実行の前の確認を分ける。値を読むこと・出来事・中の処理は受けない | 権限を見る前に処理が動くことが無い。「断った」と「別の機能が引き受けた」を区別して返せる。`UIController` の無いデバイスからも使える | 確認のイベントの使い手（権限・スライドショー）を、判断と引き受けに分けて書き直す。`UIController` が本体を変える 62 か所（所有権を取る 25 か所を含む）を書き換える |
| B | A に加え、値を読むことと出来事も窓口が中継する | 問い合わせ先が完全に 1 つになる | 部品をまたぐ呼び出し（Udon では同じ部品の中より遅い[8]）が、毎フレームの読み取りの分だけ増える。機能を足すたびに窓口を書き換える |
| C | 権限の確認だけを窓口に集め、命令は今のまま UI が本体を呼ぶ | 手間が小さい | 確認を飛ばして本体を呼ぶ道が、UI の数だけ残る（P5） |
| D | 今の確認のイベント（`BeforeUserXxx`）を、そのまま窓口に移す | 今の作りに近く、手間が小さい | 権限の確認と操作の置き換えが混ざったまま。登録の順番によっては、権限を見る前にスライドが動く（P2）。断ったのか引き受けたのかを区別できない。照会でも知らせの処理が動く（P3） |

**表 4** 窓口の段（案 A）

| 段 | すること | 副作用 |
| --- | --- | --- |
| 1. 受付 | デバイスから、操作の種類（定数）と引数を受け取る。あとから届く結果（URL からのプレイリストの読み込みなど）を返す先として、呼んだ物を添えられる | 無し |
| 2. 権限の判断 | 登録された判断に、「この人はこの操作をできるか」を聞く。1 つでも「できない」なら断る | 無し（知らせを出さない。状態を変えない） |
| 3. 振り分け | 登録された引き受け手に、この操作を引き受けるかを聞く。引き受ける物があればそこに渡し、無ければ本体の既定の処理に渡す。例：スライドモード中の前後とシークは、スライドショーが引き受ける | 無し（行き先を決めるだけ） |
| 4. 実行 | 行き先が、所有権を取って実行する | 有り |
| 結果 | 「実行した」「引き受けられた」「権限が無くて断った」「今はできない（プレイヤーが無いなど）」を返す。表示はしない | — |

**図 3** 窓口が操作を受けて流すまで（案 A）。

- **照会と実行：**
  - **照会：** 聞くだけの照会は、段 1 と 2 だけを行う。ボタンの押せる・押せないの表示に使う。
  - **実行：** 段 1〜4 を行い、段 2 は実行の直前に行う。
  - **確認のダイアログを挟む操作（URL のダイアログなど）：** 確定したときに、もう一度段 2 を行う。
- **権限は、利用者が押した操作で判断する：** 引き受け手は、引き受ける操作と同じ権限で足りる物に限る（スライドショーの「次のスライド」は、「次の曲」と同じく全員で共有する操作）。違う権限が要る処理は、別の操作として窓口に置く。
- **操作ごとの権限：** 操作によって、要る権限が違う（表 5）。窓口は、どの操作にも同じ権限を求めない。判断は、登録された物が操作ごとに答える。

**表 5** 操作の区分と、要る権限

| 区分 | 操作の例 | 判断するもの |
| --- | --- | --- |
| 全員で共有する操作 | 再生・一時停止・停止・シーク・前後・URL・リスト・キュー・リピート・シャッフル・速度・プレーヤーの切り替え・全員リロード（今の 18 種類） | 権限のモジュール（Editor 以上。今と同じ） |
| モジュールの共有の設定 | 音程、スライドショーのモードと秒数 | 権限のモジュール（Editor 以上。#211 で足す挙動の変更、D4） |
| モジュールに固有の決まりがある操作 | 自動再生(Owner) の URL を変える | モジュール自身の判断（インスタンスのオーナーだけ。今と同じ）。権限のモジュールは答えない |
| 見る人ごとの操作 | 音量・ミュート・明るさ・左右反転・ずれの補正・解像度・言語・自分の読み込み直し（今の 8 種類） | 判断しない（誰でもできる。今と同じ） |

- **表示（D2）：** 窓口は結果を返すだけで、知らせを出さない。表示は、呼んだデバイスが決める。
  - **ダイアログのある UI（本体のスクリーン・タブレット）：** 断ったことをダイアログに出す。`UIController` に、結果から知らせを出す共通の補助を置く。
  - **ダイアログの無い小さなデバイス（Controller Bar・Playlist Panel・全員リロードボタン）：** 照会で、できない操作のボタンを押せない見た目にする。全員リロードボタンの NO ACCESS も照会で出し、今の毎秒の確認を置き換える。
  - **権限が変わったとき：** 権限のモジュールは、今も権限が変わったことを知らせている（`AfterPermissionChanged`）。窓口がそれを中継し、照会で表示を決めるデバイスは、そのときに表示を直す。照会を毎フレーム繰り返さない。
- **迂回の見つけ方：** 窓口を置くだけでは、迂回は防げない。自動再生やネットワークの受信のために、本体の命令は呼べるまま残す。そのため、新しいデバイスが誤って本体を呼べば、窓口を通らない。次の 3 つを組み合わせる。
  1. 利用者の操作の口を、窓口に集める。デバイスが使う操作は、すべて窓口にある。
  2. 参照の用途を分ける。デバイスと UI は、操作に窓口を使い、状態を読むことと出来事の登録に本体を使う。
  3. エディターの検査で、デバイス・UI・モジュールの UI のコードが、本体の状態を変える呼び出し（命令・設定の書き込み・所有権を取る）をしていないかを見つける。許すのは、読む物と出来事の登録だけにする。
- **依存の向き：** 窓口は、`PlaylistLoader`・ピッチシフター・スライドショーなどを参照しない。モジュールが、窓口に権限の判断・引き受け手・URL の差し込み口を登録する。依存は、モジュールから共通の層への向きだけにする。
- **今の確認のイベントの置き換え：**
  - **分け方：** `BeforeUserXxx` は、権限の判断と操作の引き受けの 2 つの登録に分けて置き換える。
  - **無くす物：** 操作を移し終えたら、`UIController` の確認のイベント（`InvokeBeforeEvent`・`CancelCurrentAction`）と、中止を伝える 1 つの旗（`_actionCancelled`）を無くす。二重の仕組みは残さない。
  - **無くなる制約：** 判断は副作用を持たないので、今の「確認の中で別の確認を送れない」制約も無くなる。URL の差し込み口が専用の欄になったのは、この制約のためである。
- **無くすのは、権限の部品の写しだけ：** モジュールの画面（設定の行、自動再生(Owner) のカード、権限の一覧）を UI に置く差し込み口（`uiSlots`）は残す（§4.6）。権限の一覧の画面も、置ける UI に残す。
- **窓口を通らない物：**
  - 値を読むこと（再生位置・状態・曲名など）。今のまま本体から読む。
  - 出来事（`AfterXxx`・名前の出来事）。今のまま本体に登録して受ける。
  - 中の処理（自動再生・全員リロードの受信・設定の復元・リトライ）。今のまま本体を直接呼ぶ。
  - UI だけの仕事（表示・翻訳・ダイアログ）。今のまま `UIController` が受け持つ。
  - デバイスが自分だけで持つ同期（タブレットの画像アプリの画面と一覧）。今のままデバイスが持ち、権限は通らない。
- **重さ：** 操作のたびに、部品をまたぐ呼び出し（受付・判断・振り分け）が増える。UdonSharp では、部品をまたぐ呼び出しは同じ部品の中の呼び出しより遅い[8]。毎フレームの読み取りは窓口を通さないので、増えるのは操作の回数分だけである。部品の数が減っても、速度やメモリが良くなるとは言えない。
- **挙動が変わる所：**
  - **Controller Bar と Playlist Panel（D3）：** 窓口を通るので、権限がかかるようになる。
  - **スライドショーの前後とシーク：** 権限の判断が振り分けより前になるので、スライドモードでも必ず権限を見る。今は、登録の順番によっては見ないことがある。
  - **音程とスライドショーの設定（D4、#211）：** 窓口の骨組みができたあとに、#211 で直す。モジュールの UI は、設定を変える操作を窓口に渡し、権限のモジュールが判断する（Editor 以上）。

### 4.4 デバイスのことはデバイスに置く（P8・P9）

- **インスペクターの区画（D8）：** Sub Controller のインスペクターは、根元の下の部品の型を見て、その型に「区画」を登録したエディターのクラスがあれば、その区画を描く。
  - 例：タブレットの戻す設定と訪問者の顔写真を、タブレットの区画に移す。#206 の案内も、その区画に入る。
  - 共通のインスペクターに残すのは、色の組・言語・待ち受け画像・プレイヤーの欄のように、どのデバイスにもある物だけにする。
  - VVMW の Core のインスペクターが、操作する部品の設定を埋め込むのと同じ考えで、登録はエディターの属性で行う。
  - **小さく始める：** まずタブレットの区画の移動だけを作る。区画を登録する属性は 1 つに留め、VVMW の `[Locatable]`・`[Resolve]` のような汎用の属性の仕組みは作らない。
- **ビルドの処理：**
  - デバイスに固有のビルド処理は、デバイスの側のフォルダーに置く。今のタブレットの訪問者の記録の処理は、共通の `Editor/Build/` にある。
  - 「デバイスがどのプレイヤーに従うか」を、共通の補助として用意する。タブレットと全員リロードボタンは、それを使う。
  - 「ワールドに 1 つだけ残す」は、使うのがタブレットの訪問者の記録だけなので、共通の仕組み（VVMW の `ISingleton` のような物）は作らず、今の専用の処理をタブレットの側に移すだけにする。2 つ目が要るようになったら、共通にする。
- **全員リロードボタン：** 権限を聞くためだけに持っていた `UIController` と空の `Canvas/Modules` は、窓口のあとは要らなくなる見込みである。外すかは、色や翻訳に使っていないかを確かめて、子の issue で決める。

### 4.7 取り入れないもの

- **VVMW の土台への依存：** §5 の D11。
- **プレイリストとキューを窓口に移すこと：** VVMW の `FrontendHandler` はプレイリストとキューを持つが、KawaPlayer では本体（`Controller`・`QueueList`・`HistoryList`）が持って同期している。移すと同期の作りが変わる。窓口が受け持つのは、利用者の操作の入口だけにする。
- **値を読むことと出来事の中継：** 表 3 の B。
- **受ける側（本体）で権限を確かめること：** VVMW の `FrontendHandler` は、受けた命令のうち 5 つをロックで断る。KawaPlayer の本体は、利用者の操作と中の処理（自動再生・リトライなど）を見分けられない。窓口には利用者の操作だけが来るので、見分けが要らない。
- **ビルドでのイベントの購読（属性）：** 表 7 の B。今の実行時の登録で困っていない。
- **持てる・戻す・同期の作りの統一（P14）：** 持てるデバイスは今 2 つで、作りの違いが困りごとになっていない。3 つ目の持てるデバイスを足すときに見直す。
- **複数のプレイヤーの切り替え（VVMW の `ActiveRegionManager`）：** KawaPlayer のデバイスは、1 台のプレイヤーに従う作りで足りている。

## 8. まとめ

- **中心：** プレイヤーごとに 1 つの窓口を置く。窓口は、権限の判断と操作の受付を分けた、利用者の操作の層である。受付 → 権限の判断 → 振り分け → 実行の順に流し、結果を返す。表示はデバイスが決める。
- **守る物：** 権限の判断は副作用を持たず、照会と実行を分ける。モジュールは窓口に登録し、窓口はモジュールを知らない。迂回は、窓口に加えてエディターの検査で見つける。
- **ほかの 3 つの考え：** 「正の値を 1 つ」「デバイスのことはデバイスに」「接続口に名前」。
- **VVMW から取り入れる物：**
  - `FrontendHandler` のように、受け口を本体ごとに 1 つにする考え。VVMW より広く、利用者の操作をすべて通す。
  - つなぎ方を部品の側で決める考え。
  - 置くときに結ぶ考え。

  土台のパッケージには依存しない。
- **残す物：** KawaPlayer の細かい権限（操作ごと、全員で共有）、値の読み方と出来事の受け方、中の処理の呼び方、プレイリストとキューの持ち場、同期のしかた、UI の差し込み口の仕組み。
- **進め方：** 決めることは 13 個（D1〜D13）。実装は子の issue 8 つと、先に直す 2 つに分ける。窓口は、小さな操作で確かめてから広げ、権限の漏れを直す所は挙動の変更として明示する。
