## 要旨

KawaPlayer のデバイス（タブレット・ボタン・パネルなど）は、本体へのつなぎ方がデバイスごとに少しずつ違う。新しいデバイスを足すたびに、共通のインスペクターやビルド処理に手を入れている（#255）。

同じことを VizVid（VVMW）がどうしているかを比べると、VVMW は、つなぎ方を部品の欄で宣言し、ビルドで結んでいた。デバイスに固有の処理は部品の側に置かれ、共通のコードは個別の部品を知らない（[comparison.md](comparison.md)）。

この文書は、KawaPlayer の接続口を、次の 4 つの考えで整理する方針を示す。

1. **正の値を 1 つにする：** どのプレイヤーに従うかを、デバイスの根元の 1 か所に持つ。
2. **デバイスのことはデバイスに置く：** デバイスの設定とビルドの処理を、デバイスの側に置く。
3. **接続口に名前を付ける：** 名前のイベントや UI の差し込み先に、一覧と名前を付ける。
4. **配る仕組みを 1 つの形にする：** イベントの配り先のリストを、同じ形にそろえる。

VVMW の土台のパッケージには依存せず、同じ考えを小さく自前で作ることをすすめる。決めることは 10 個（D1〜D10）あり、それぞれにおすすめを付けた。実装は子の issue 4 つに分け、見つかった不具合（AudioLink）と #206 の 2 つは先に直す。整理の入る版は、1.3.0 のあとをすすめる。

**キーワード：** デバイス、接続口、方針、正の値、ビルド時の処理、イベント、権限、VizVid

## 1. はじめに

### 1.1 背景

KawaPlayer の本体の横には、Controller Bar・Playlist Panel・Sub Screen・タブレット・全員リロードボタンの 5 種類のデバイスを置ける。タブレットや全員リロードボタンのように、これからもデバイスは増える。

#255 で今のつなぎ方を分析すると、次のことが分かった。

- つなぎ込みは、エディター・ビルド・実行時の 3 段に分かれている。
- 部品が「どのプレイヤーに従うか」を見つける方法が 3 通りある。
- タブレットの設定が、共通のインスペクターに入っている。
- 名前で呼ぶ接続口に一覧が無く、受け手が登録先を取り違えている所もあった（AudioLink）。

整理の論点は O1〜O8 として挙げた。#256 では、作りの成熟している VVMW と比べ（[comparison.md](comparison.md)）、そのうえで方針を決める。

### 1.2 目的

実装の前に、次の 3 つをまとめる。

1. KawaPlayer の問題と、その根拠と影響（§3）。
2. 問題ごとの直し方の案と、おすすめ（§4・§5）。
3. 確かめ方と進め方（§6・§7）。

この文書では実装しない。実装は、決めたことを子の issue に分けて行う（§7）。

### 1.3 読み方と、文書の分け方

- **この文書（方針）：** 何を直すか、どう直すかと、その理由を書く。決まったら、§5 に答えを書き込んで固める。
- **[comparison.md](comparison.md)（仕様と比較）：** KawaPlayer と VVMW が今どうつないでいるかを、機能ごとに並べた事実の記録。
- **[device-connections.md](../../analysis/device-connections.md)（現状の分析）：** KawaPlayer の接続口 E1〜E12 と論点 O1〜O8。この文書では、その番号を使う。

急ぐときは、§4.1（基本の方針）、§5（決めること）、§7（進め方）を読めば足りる。

## 4. 直し方

### 4.1 基本の方針

![デバイスの根元の部品が、どのプレイヤーに従うかを持つ。ビルドのデバイスの処理が、それをもとに下の部品の参照を書き直して確かめる。デバイスのインスペクターの区画とビルドの処理はデバイスの側に置き、モジュールの UI は名前の付いた差し込み先に写す。イベントの名前は 1 つの一覧にまとめる](images/proposal.svg)

**図 1** 整理したあとのつなぎ方（案）。

1. **正の値を 1 つにする（P1・P2）：**
   - **正の値：** デバイスの根元の `YamaPlayerSubController.YamaPlayer` を、どのプレイヤーに従うかの唯一の値にする。
   - **ビルド：** 下の部品の参照は、ビルドがこの値から書き直す。食い違いと未設定はログに出す。
   - **エディター：** インスペクターでの書き込みは、エディターですぐ見た目に出すためだけに残す。
2. **デバイスのことはデバイスに置く（P3・P4）：** デバイスのインスペクターの設定とビルドの処理を、デバイスの側に置く。共通のコード（Sub Controller のインスペクター、本体のビルド処理）は、個別のデバイスを知らない。
3. **接続口に名前を付ける（P5・P7・P8）：** 名前で呼ぶイベントと差し込み口に、1 つの一覧（定数）を作る。UI の差し込み先には、パスの代わりに名前を付ける。UI の中を外から読む所は、公開の窓口にする。
4. **配る仕組みを 1 つの形にする（P6）：** 配り先のリストの扱い（足す・配る）を共通の補助にそろえ、送り先と受け手の登録先の食い違いを無くす。
5. **VVMW の土台には依存しない（D1）：** vrcw-foundation の属性・前処理・基底クラスは使わず、上の考えを KawaPlayer の中で小さく作る。理由は §5 の D1。
6. **守ること：**
   - **Network ID：** 出荷済みのプレハブで、U# の部品がすでにある物に、U# の部品を足したり外したりしない。足す物は、子の物に置くか、ビルドで消える U# でない部品にする。
   - **SDK の下限：** U# は、最低の SDK（3.10.2）でコンパイルできるようにする。
   - **互換の方針：** 互換のためだけのコードは残さない。ただし、既存のプロジェクトを新しい版に更新したあとの動きは確かめ、移行が要るなら手順を案内する（CLAUDE.md の Compatibility & Technical Debt Policy）。

### 4.2 正の値と、デバイスの足し方（P1・P2）

**表 3** 正の値の選択肢

| 案 | 中身 | 良いところ | 気になるところ |
| --- | --- | --- | --- |
| **A（おすすめ）** | `YamaPlayerSubController.YamaPlayer` を正の値にする。新しいビルド処理（デバイスの処理、モジュールの処理より前）が、根元の下の `UIController._controller`・`YamaPlayerScreen.controller`・`YamaPlayerSpeaker.controller` を書き直す。違う値が入っていたら、ログに出す | 部品のクラスと GUID が変わらず、保存された値（選んだプレイヤー）がそのまま使える。下の部品を足しても、選び直さずにつながる | ビルド処理が 1 つ増える |
| B | VVMW のように、各部品の欄に「たどる」属性を付け、汎用のビルド処理が埋める | 部品ごとに、たどり方を書ける | 汎用の仕組みを作る手間が大きい。KawaPlayer のデバイスは、どれも「根元のプレイヤーに従う」だけで、たどり方を変える必要がない |
| C | 今のまま | 手間が無い | P1・P2 が残る |

- **未設定のデバイス（D3）：** プレイヤーを選んでいないデバイスは、今は全員リロードボタンだけが、ビルドで外されてログに出る。ほかのデバイスも同じ扱いにそろえることをすすめる。選んでいないデバイスは、どのみち動かないためである。
- **置くときに結ぶ（D8）：** `GameObject > KawaPlayer > …` で置くとき、プレイヤーを自動で選ぶ。選び方の順番は次のとおり。
  1. 選んでいる物の親をたどって、いちばん近い KawaPlayer。
  2. シーンに KawaPlayer が 1 つだけなら、それ。
  3. どちらでもなければ、選ばずに案内を出す。

  VVMW の `Locate` に当たる。VVMW のように、無ければ本体を置くことはしない。

### 4.3 デバイスのことはデバイスに置く（P3・P4）

- **インスペクターの区画（D4）：** Sub Controller のインスペクターは、根元の下の部品の型を見て、その型に「区画」を登録したエディターのクラスがあれば、その区画を描く。
  - 例：タブレットの戻す設定と訪問者の顔写真を、タブレットの区画に移す。#206 の案内も、その区画に入る。
  - 共通のインスペクターに残すのは、色の組・言語・待ち受け画像・プレイヤーの欄のように、どのデバイスにもある物だけにする。
  - VVMW の Core のインスペクターが、操作する部品の設定を埋め込むのと同じ考えで、登録はエディターの属性で行う。
- **ビルドの処理：**
  - デバイスに固有のビルド処理は、デバイスの側のフォルダーに置く。今のタブレットの訪問者の記録の処理は、共通の `Editor/Build/` にある。
  - 「デバイスがどのプレイヤーに従うか」と「ワールドに 1 つだけ残す」の 2 つを、共通の補助として用意する。タブレットの訪問者の記録と全員リロードボタンは、それを使う。

### 4.4 名前の一覧と、配る仕組み（P5・P6・P8）

### 4.7 取り入れないもの

- **VVMW の土台への依存：** §5 の D1。
- **ビルドでのイベントの購読（属性）：** 表 4 の B。今の実行時の登録で困っていない。
- **持てる・戻す・同期の作りの統一（P10）：** 持てるデバイスは今 2 つで、作りの違いが困りごとになっていない。3 つ目の持てるデバイスを足すときに見直す。
- **複数のプレイヤーの切り替え（VVMW の `ActiveRegionManager`）：** KawaPlayer のデバイスは、1 台のプレイヤーに従う作りで足りている。

## 8. まとめ

- **4 つの考え：** KawaPlayer の接続口を、「正の値を 1 つ」「デバイスのことはデバイスに」「接続口に名前」「配る仕組みを 1 つの形に」で整理する。
