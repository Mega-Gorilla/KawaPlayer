## 要旨

KawaPlayer では、エラーや読み込み中のまま自分の画面だけ止まると、読み込み直しを押しても戻せない（#215）。同じ場面を VizVid（VVMW）がどう扱っているかを機能ごとに比べ（[comparison.md](comparison.md)）、その結果から KawaPlayer の問題を 9 件挙げた。テスト用の Unity と VRChat（Build & Test、同じ PC の 2〜3 クライアント）で、今の動きも確かめた。方針としては、位置の基準（ネットワークの時計）は KawaPlayer のまま残し（時計の取り方は直す）、自分の画面だけの復旧の作りを VVMW から取り入れることを提案する。この文書は、問題ごとの選択肢、難しさの見積もり、1.3.0 に入れるかの決め方、決めていただくこと、確かめ方をまとめる。

**キーワード：** 再生の同期、読み込み直し、rate limit、バッファ、方針、1.3.0

## 1. はじめに

### 1.1 背景

スクリーンの左の列の **読み込み直し** は、自分の画面で今の動画を読み込み直し、ほかの人と同じ位置から再生し直すボタンである。映像や音が止まったとき、ずれが直らないとき、ライブ配信で遅れたときに使う。

ところが、自分の画面がエラーや読み込み中で止まっているときには、このボタンは何もしない（#215）。ほかの人が再生を続けていても、止まった人は次の曲になるまで見られない。いちばん戻したい場面で戻せないことになる。

直す前に、同期の作りが成熟している VizVid（以下 VVMW）と比べた。すると、位置の決め方、共有する状態の分け方、読み込みの間引き、バッファの扱いなどで、作りが大きく違うことが分かった。#215 だけを直すより、先に全体の方針を決めたほうがよいと考え、この文書を書いた。

### 1.2 目的

方針を決めていただくための材料を、次の 3 つにまとめる。

1. KawaPlayer の問題を洗い出し、それぞれの根拠と影響を示す（§3）。
2. 問題ごとの選択肢とおすすめを示す（§4）。
3. 難しさを見積もり、決めることを質問の形で並べる（§5）。

この文書では実装しない。決まったことは、子の issue に分けて作る（#228）。

### 1.3 読み方と、2 つの文書の分け方

- **この文書（方針）：** 何を直すか、どう直すか、どう決めるかを書く。決まった時点で固まる記録である。
- **[comparison.md](comparison.md)（仕様と比較）：** KawaPlayer と VVMW が今どう動くかを、機能ごとに並べた事実の記録である。調べた時点（`803126b`・`834bd5e`）のもので、実装すると KawaPlayer の動きは変わる。変わったあとの KawaPlayer の仕様は、実装の PR で `docs/analysis/` に別に書く。

急ぐときは、§2（比べて分かったこと）、§4.1（基本の方針）、§5.4（決めること）を読めば足りる。場面の記号（S1〜S11）は、比較の文書の表 1 のものである。

## 2. 比べて分かったこと

詳しくは [comparison.md](comparison.md) にある。方針に関わる事実を、短くまとめる。

- **位置の基準：** KawaPlayer はネットワークの時計を、VVMW はオーナーの実際の再生位置を基準にする。KawaPlayer では、後から入った人も止まった人も、オーナーに頼まずに位置を計算できる。ただし、KawaPlayer が使う時計（`GetNetworkDateTime`）は、VRChat で日時の同期に失敗したクライアントで、ずれたまま直らなかった。VVMW が使うサーバーの時刻（`GetServerTimeInMilliseconds`）は、同じクライアントでも合っていた（[比較の §5](comparison.md#5-位置の決め方)）。
- **自分の画面だけの復旧：** KawaPlayer の読み込み直しは、エラーや読み込み中の画面からは何もしない。VVMW は、共有する状態と自分の読み込みの状態を分けており、どの状態からでも、同期している URL で読み直せる（[比較の §7](comparison.md#7-自分の画面だけの復旧読み込み直し)）。
- **読み込み直しのときの送信：** どちらも読み込み中は値を送らない。ただし、オーナーが読み直すと、どちらも時刻を書いて送信を要求する（KawaPlayer は準備完了のあとの位置合わせ、VVMW は準備完了のあとの再生）。VVMW がそのとき書く開始の時刻は、Unity（Unity Video Player）では 0.5 秒だけ位置を合わせる前の値だったが、VRChat の AVPro では初めから正しく、ほかの人の画面も動かなかった。KawaPlayer の書き換えも、VRChat でほかの人の画面を動かさなかった（同じく §7）。
- **VVMW の予約の読み込み：** VVMW で読み込み直しを続けて押すと、予約は 1 つにまとまるが、予約の読み込みは読み込み直しの印が消えたあとに走り、0 秒から再生した。オーナーが押すと、VRChat（2 クライアント）では、ほかの人の画面も先頭に戻った（[比較の §8](comparison.md#8-読み込みの間引き)）。
- **権限とローカルモード：** KawaPlayer の読み込み直しは、PermissionManagement があると Editor 以上でなければ押せない。ローカルモード（`IsLocal`）では、同期する曲の値が空のことがある（同じく §7）。
- **読み込みの間引き：** VRChat は、1 人が新しい URL を読めるのを、すべての動画プレイヤーを合わせて 5 秒に 1 回に限る [3]。KawaPlayer が間隔をあけるのはリトライだけで、VVMW はすべての読み込みを並べる（[比較の §8](comparison.md#8-読み込みの間引き)）。
- **ずれとバッファ：** KawaPlayer は 5 秒ごとに 0.3 秒以上でシークし、バッファを区別しない。VVMW は 0.5 秒ごとに 0.9 秒以上でシークし、バッファ中はシークしない。モデルでは、KawaPlayer がシークを繰り返すおそれがある（[比較の §6](comparison.md#6-ずれの補正とバッファ)、図 5）。
- **オーナーの交代：** 次のオーナーの画面が、読み込み直しではない読み込みの途中だと、その準備完了で位置 0 が送られ、全員が先頭に戻る。VRChat の 3 クライアントで再現した（[比較の §10](comparison.md#10-オーナーが替わるとき)）。
- **Unity と VRChat で確かめたこと：** P1（エラーと読み込み中で読み込み直しが効かない）、P2（ボタンが押せるまま）、P3（オーナーの読み込み直しで同期する時刻が書き換わる）、P7 の経路を、テスト用の Unity（ClientSim、1 クライアント）で確かめた。そのあと VRChat の Build & Test で、ほかの人の画面（P3、VVMW の予約の読み込み）、オーナーの交代（P7）、時計のずれ（P9）を確かめた（[比較の付録 D](comparison.md#付録-dunity-での確認2026-10-14)・[付録 E](comparison.md#付録-evrchat-での確認2026-10-14)）。
- **KawaPlayer の良いところ：** 時計が基準であること、何度試しても直らない Access Denied をリトライしないこと、エラーの詳細を見られることは、VVMW より優れている（[比較の §13](comparison.md#13-まとめそれぞれの良いところ)）。

P1〜P5 は、どれも「自分の画面だけの復旧」に関わり、同じ経路（`Reload` から読み込み、準備完了まで）を通る。まとめて直すのが自然である。P6 は、直し方の数値を実機で決める必要がある。P7 は VRChat で再現したので、直し方は決まっている。P8 は新しい機能で、誰が押せるかを先に決める必要がある。P9 は、時計の取り方を替えれば直せる見込みである。

P3 を直すのは、VVMW に合わせるためではない（VVMW も、オーナーが読み直すと値を送る）。「読み込み直しは自分だけ」を、KawaPlayer として守るためである。

KawaPlayer に「オーナーへの送り直しの依頼」がないことは、問題に数えない。受け取った時刻から位置を戻すためには要らないからである（[比較の §11](comparison.md#11-オーナーへの依頼と全員の読み込み直し)）。状態そのものを取り直す役目（VVMW では、初めの同期や、欠けた状態の取り直しにも使っている）は、今回は扱わない。

## 4. 提案

### 4.1 基本の方針

**位置の基準は KawaPlayer のまま残し、自分の画面だけの復旧の作りを VVMW から取り入れる。**

時計を基準にする作りは、後から入った人も止まった人も、オーナーに頼まずに位置を計算できる点で、VVMW より簡単で強い（D1 で決定）。ただし、時計の取り方は直す（§4.5 の P9）。取り入れたいのは、VVMW の「全員が共有する状態」と「自分の読み込みの状態」を分ける考え方である。KawaPlayer では、自分の画面の復旧を **「受け取った共有の状態を、自分の画面にもう一度当て直すこと」** として作るのが素直である。`OnDeserialization` が曲の版の変化を見て読み込むところを、版を見ずに通す形になる。

ただし、これが当てはまるのは、共有の値を受け取る側（オーナーではない人）だけである。ローカルモード（`IsLocal`）では共有の値を送らないので、同期する曲の値（`_url` など）は空のことがある。オーナーも、新しい曲を始めた直後は、送るための値（`OnPreSerialization` が今の曲から作る）がまだ古いことがある。Unity（ClientSim、1 クライアント）では、オーナーの手元の `_url` は再生中もずっと空だった（比較の付録 D の 6）。VVMW の `LocalSync` は、オーナーでも同期する URL を読み直すので、送らない ClientSim では前の URL を読み直した（比較の付録 D の V1）。VRChat でも、送る前なら同じことが起きる。オーナーが今の曲を使うのは、これを避けるためでもある。そのため、**オーナーではない人は受け取った同期の曲を、ローカルモードとオーナーは今の曲（`Track`）を** 読み直す（図 1）。

### 4.2 自分の画面だけの復旧（P1〜P5）

| | C：ワールドで 1 つにする（VVMW と同じ） | KawaPlayer を 2 台置いても断られない | 大。新しいオブジェクトと、ビルドでの結び付けが要る |

速度と最大の画質を変えると、KawaPlayer は自動で `Reload` を呼ぶ（`Controller.UpdateSpeed`・`MaxResolution`）。読み込み中に受け付けない N 秒の決まりや間引きが、この自動の読み込み直しを落とさないようにする（たとえば、待っているあいだの頼みとしてまとめる）。

**VVMW から学ぶこと：** VVMW では、予約してまとめた読み込みが、読み込み直しの印が消えたあとに走り、新しい再生として 0 秒から再生された。オーナーが押すと、VRChat では全員が先頭に戻った（比較の §8、付録 D の V1・V3、付録 E の E2）。KawaPlayer では、読み込み直しの印を、予約した最後の読み込みが終わるまで残す。復旧の準備完了では、オーナーでも位置 0 を送らない（P3 の、送らない位置合わせと同じ）。

読み込み中に読み直しを受け付けるまでの時間 N は、15 秒にする（D4）。VVMW のように待たずに受け付けると、遅いだけの正常な読み込み（VHub のリダイレクトを経るときなど）も、押せば最初からになってしまう。初めは 10 秒を仮の値にしていたが、VRChat の確認では、正常な読み込みが 4.2〜8.1 秒かかった（比較の付録 E。archive.org の mp4、AVPro、速い PC）。VRChat は URL を yt-dlp で解決するだけで 3〜5 秒かかっており、YouTube や VHub の曲はもっと長くなる見込みなので、余裕をとった。短すぎると遅いだけの読み込みをやり直させ、長すぎても止まった人が数秒長く待つだけである。エラーで止まったときは、N に関係なくすぐに押せる。N は 5.1 秒の間引きより長いので、N のあとの読み込みが間引きで待たされることもない。N は `Controller` に保存される値にせず、コードの定数にする（保存される値は、既存のワールドに古い値が残る。P6 の `_syncMargin`・`_syncFrequency` と同じ問題）。T2 で確かめる。

### 4.3 時刻合わせとオーナーの交代（P6・P7）

- **P6 時刻合わせ：** 今の「5 秒ごと、0.3 秒以上でシーク。バッファを区別しない」は、VVMW の「0.5 秒ごと、0.9 秒以上でシーク。バッファ中は待つ」と大きく違う。モデルでは、シークの手間が 0.3 秒を超えると、5 秒ごとのシークの繰り返しになる（比較の図 5）。VRChat でも、オーナーの読み込み直しの 5 秒後に、オーナー自身がもう一度シークして値を送り直した（比較の付録 E の E4）。次の 3 つを合わせて、VVMW の考え方に合わせる（D9 で決定）。
  - 位置が進んでいないあいだ（バッファ中）はシークしない
  - 境目を、シークの手間より大きくする（★ VVMW と同じ 0.9 秒。速度の分も考える）
  - 確かめる間隔を短くする（★ 1 秒。上の 2 つと一緒でないと、シークが増えるだけになる）

  その代わり、0.9 秒より小さなずれは直さなくなる。回線のよいときは、もともと大きくずれない（VRChat の 3 クライアントでは、0.02 秒以内で合っていた）。実機の測定（T8）は、数値を決めることと、直したあとの確認に使う。境目と間隔は `Controller` に保存される値（`_syncMargin`・`_syncFrequency`）なので、既存のワールドに保存された値をどう扱うかも、実装で決める。
- **P7 オーナーの交代：** VRChat の 3 クライアントで再現した（比較の §10、付録 E の E5）。準備完了のときに位置 0 を送るのを、オーナー自身がその曲を始めたとき（曲の版を自分で増やしたとき）だけにする。直す手間は小さい。

### 4.4 全員の読み込み直し（P8）

全員の読み込み直し（VVMW の `GlobalSync` にあたるもの）は、イベントやライブで役に立つ。ただし、誰でも全員の再生を止められる。PermissionManagement の Editor 以上に限り、読み込みの間引きも通す。自分の画面にしか効かない読み込み直しは権限の対象から外す（D3）が、全員に効く P8 は権限を残す。1.3.0 に入れる（D6・D7）。

### 4.5 時計の取り方（P9）

KawaPlayer は、位置の計算に `GetNetworkDateTime` を使う（`Controller.Sync`）。VRChat で、日時の同期に失敗したクライアントだけ、KawaPlayer が 2.15 秒ずれたまま直らなかった。同じクライアントの VVMW（`GetServerTimeInMilliseconds`）は合っていた（比較の §5、付録 E の E6）。選択肢は次の 3 つで、A に決まった（D8）。

- ★**A：** 同期する時刻を、VRChat のサーバーの時刻（`GetServerTimeInMilliseconds`）にする。差は `Networking.CalculateServerDeltaTime` で計算する（ミリ秒の値は 32 ビットで一巡するので、そのまま引き算しない）。VVMW と同じ時計で、今回のクライアントでも合っていた。
- **B：** `GetNetworkDateTime` のまま、同期の失敗を見分けて、失敗したらサーバーの時刻に切り替える。見分ける確かな方法がない。
- **C：** 今のまま。PC の時計がずれた人は、同期に失敗するとずれ続ける。

A の手間は小〜中である。同期する値の意味が変わるが、1 つのインスタンスの全員は同じワールドのビルドを読むので、古い値と混ざることはない。確かめ方は T17。タブレットの訪問者の記録は、表示する日時として `GetNetworkDateTime` を使っており、この話とは別である。

### 4.6 取り入れないもの

- **オーナーへの送り直しの依頼（`OwnerSync`）：** 受け取った時刻から位置を戻すためには要らない。状態そのものを取り直す役目（初めの同期や、欠けた状態の取り直し）は、今回は扱わない。
- **オーナーの位置を基準にする時刻の作り：** 今の作りを変えるほどの利点がなく、既存のワールドでの動きが大きく変わる。

VVMW は MIT ライセンスである。取り入れるのは考え方で、コードは KawaPlayer の作りに合わせて書く。参考にしたことは、コードのコメントと PR に書く。

## 5. 方針の決め方

### 5.1 判断の基準

問題ごとに、次の 4 つで判断する。

1. **影響：** 誰に、どのくらいの頻度で、どのくらい困るか。
2. **根拠の確かさ：** コードで確かめたか、実機での再現が要るか。
3. **難しさ：** 実装と確認にかかる手間（§5.2）。
4. **互換の危険：** 既存のワールドを壊さないか。たとえば、出荷したプレハブの UdonBehaviour を足したり減らしたりしない、U# が SDK 3.10.2 でコンパイルできる、といった CLAUDE.md の約束を守れるか。

## 8. まとめ

KawaPlayer と VVMW を機能ごとに比べると、位置の基準は KawaPlayer（時計が基準）のほうが簡単で強く、自分の画面だけの復旧は VVMW のほうが整っていた。#215 の問題は、復旧の入口の条件だけでなく、値を送る経路、権限、ローカルモード、読み込みの間引きにまたがっている。そこで、P1〜P5 を 1 つの経路として作り直すことを提案する。VRChat の Build & Test では、オーナーの交代で全員が先頭に戻ること（P7）を再現し、時計の同期に失敗したクライアントがずれ続けること（P9）を見つけた。§5.4 の決めることは、すべて決まった（2026-10-14）。すべての P を 1.3.0 に入れ、読み込み直しは権限の対象から外し、N は 15 秒、間引きは読み込み直しとリトライだけ、時刻合わせは VVMW に合わせ、時計はサーバーの時刻にする。この文書をマージする直前に子の issue（A〜F）を立てて #215 を閉じ、実装に入る。
