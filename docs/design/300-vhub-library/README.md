# VHub Library 連携の実装計画

**状態: 計画案・未実装。** 作成日: 2026-10-24。2026-11-11 に、本番の構成と照らして改訂した（要点の表 2）。親は [KawaPlayer #300](https://github.com/Mega-Gorilla/KawaPlayer/issues/300)。対象リリースは未定。

ブラウザで VChat にログインし、VHub の「作成したプレイリスト」と「お気に入り」をワールドから開く。**個人ライブラリの閲覧と、選んだプレイリストを全員へ共有する操作を分ける。** ワールドに VChat / VRChat のアカウント操作権限は渡さない。

この文書の図は設計図であり、実装済みの画面や成功した実機テストの画像ではない。数値・API 経路・クラス名の案は PoC 後に確定する。

## 1. 利用者から見た流れ

![WebでVChatログインし、閲覧専用URLを入力し、自分の一覧から選んだ1件だけを共有する4段階](images/journey.svg)

図1. 最初に Web で認証し、VRChat 内では一覧から選ぶ。ログイン情報を動画 URL 欄に貼る手順ではない。

1. PC / スマートフォン等のブラウザで VHub に VChat ログインする。
2. Web の「VRChat と連携」で、許可する対象と期限を確認して連携 URL を発行する。
3. KawaPlayer の専用 URL 欄へ貼るか、欄に入っている前半の続きにコードを打って、接続する（入力の軽くし方は 6.5）。初期版では各訪問時の手動接続を基本とし、端末 / ワールドをまたぐ自動ログインは約束しない。
4. 自分のクライアントだけで「作成したプレイリスト」「お気に入り」を見る。ここでは Controller の所有権も共有スロットも変更しない。
5. 選んだリストの取得後、既存の再生権限と、必要なら古いリストとの入替確認を通して共有へ追加する。全員への反映と、停止中だけの自動再生は既存 PlaylistLoader の規則を使う。

閲覧をインスタンスオーナー限定にはしない。**閲覧の許可は VHub の grant、ワールドへ追加する許可は既存 KawaPlayer の権限**であり、別の判定になる。

## 4. 個人用と共有用の境界

![個人カタログとローカルモジュールの間だけで連携URLを使い、公開リストは番号のURLで読んでIDを照合し、非公開リストはカタログの曲を使い、権限確認後に選んだプレイリストだけを共有する構成](images/boundaries.svg)

図3. 右側へ同期するのは、個人キーを含まない選択済みリストのデータだけ。公開のリストは更新用の番号の URL も同期し、非公開のリストは取得元の URL を同期しない（6.6）。図の URL は通信設計の分類であり、秘密を図中に埋め込んでいない。

### 4.1 ワールドはアカウントへログインしない

連携 URL は通常のログイントークンとは別の **閲覧用の鍵（grant）**。所持者は期限内に許可範囲を読めるが、アカウント設定・VChat 投稿・お気に入りの変更等はできない。IP、VRChat の表示名、`playerId` を鍵の代わりの本人確認に使わない。

キーはサーバーで乱数発行し、ハッシュだけを保存する。ブラウザで見せる生キーは発行時だけとし、再発行は別キーにする。所有者・期限・許可範囲・失効をサーバーで判定し、再起動で失効が解除されないよう永続化する。

### 4.2 共有の境界

- 個人 URL、接続状態、ライブラリ一覧はモジュールのローカル状態だけに置く。ログ・エラー・コピー欄へキーを出さない。
- `DynamicPlaylist.Fill` へ渡す source は、**キーを含まない公開プレイリストの取得先**（`/vrcurl/resolve/{i}`）と、応答から作る識別（`default/{id}`）。一覧を読むだけで Fill しない。
- 選択した ID と応答 ID の一致を、所有権取得・共有データ書き換え・自動再生の前に確認する。番号は使い回されるので、あとの更新でも、枠を書き換える前に識別を照合する（[145-vhub-search](../145-vhub-search/README.md) の 5.2 と同じ処理）。
- 共有後の更新に個人キーは不要にする。キーのない参加者と後入り参加者でも従来の共有データで再生できる。
- 非公開のリストは、番号の URL に載せない（番号は誰でも順に読めるため）。連携 URL の応答で受け取った曲を、そのまま共有枠へ入れる。全員へ同期するのは曲と識別（`default/{id}`）だけで、取得の URL は持たない（6.6）。
- ローカルの「切断」は個人の入力・一覧・待ち処理を消すだけで、既に追加した共有リストや現在の動画を消さない。Web の「失効」とは別操作と説明する。

### 4.3 残るリスク

ローカル UI は通常の全員向け同期を避けるための設計であり、ワールド制作者・改造クライアント等からの秘匿を保証しない。SDK / VRChat、CDN、proxy、APM が URL を記録する可能性もある。自アプリのマスクだけで「キーはどのログにも残らない」とは説明しない。

連携キーは経路に入るので、途中のプロキシのアクセスログに数十日残る（3.2）。キーの寿命を短く保てば、記録の中のキーは失効のあと使えない。寿命を延ばしたくなったら、その経路をログから外す作業と組にする（D1）。

![鍵が使えるのは発行から 60 分。経路の記録は数十日残る。受け入れる（寿命を延ばさない）か、外す（一覧の経路だけログから外す）](images/key-lifetime.svg)

図4. 連携キーの寿命と、経路の記録。どちらの扱いでも、アプリのログには鍵を出さない。

PoC では記録される範囲を調べ、短命・範囲限定・失効で影響を抑え、利用者に説明する。grant の失効は後続のカタログ取得を止めるが、取得済み情報、共有済みリスト、公開 / URL 限定の取得先まで無効化するものではない。

非公開のリストも応答に入るので、有効なコードが漏れたときに読まれる範囲は、公開だけのときより広い。コードの寿命・数の上限・回数制限（D1・D5・D8）を PoC で数字にして確かめる重みが増す。発行のときに、非公開を含めるかどうかを利用者が選べるようにする（5.1）。

## 5. 両リポジトリの実装計画

### 5.1 VHub Playlist 側 — [#317](https://github.com/kisaragi-official/vhub-playlist/issues/317)

1. **Web の入口:** 既存 VChat ログインとマイライブラリから「VRChat と連携」へ案内。対象、期限、URL 所持者が読めること、非公開のリストを含めるかどうか（含めると、URL を持つ人がその中身も読める）を説明して選ばせ、発行・失効・再発行を提供する。
2. **本人と grant:** 既存セッションの userId を正とし、入力された userId を信用しない。grant のテーブル・権限・上限・ハッシュ化を追加。発行 / 失効は既存の Server Actions 方針に従う。MiAuth の追加権限は求めない。 キーの文字と長さは D8 に合わせ、区切りの `-` と大文字小文字の違いを読むときに吸収する。Web では 4 文字ずつ区切って見せ、連携 URL の全体をコピーするボタンも置く。
3. **個人カタログ:** grant を検証して、本人の自作と、お気に入りのうち公開中のものを返す。公開のリストは概要と番号、自作の非公開のリストは曲まで入れる（grant が非公開を含むときだけ。件数と大きさに上限、6.6）。同じリストが両方に入る場合は entries を重複させず、所属する欄を示す。件数と切り詰めの有無を明示する。
4. **選択先:** 検索の計画（[145-vhub-search](../145-vhub-search/README.md) の 4.2）が作る `GET /vrcurl/resolve/{i}` と `resolve` プール（使い回し型、4,096 個）を共用する。カタログを返すときに、載せた公開リストを `resolve` プールへ登録し、その番号を返す。永久の番号のプールは作らない。検索と、どちらを先に実装しても、プールと経路は 1 つにする。旧 Viewer の経路（`/vrcurl/playlist/{i}` と `/api/vrc/` の一覧）は復活させず、名前も使い回さない。
5. **曲の解決:** 選んだリストだけを解決し、既存 default 動画 Pool と曲の組み立てを再利用する。`/vrcurl/resolve/{i}` は、キャッシュを読む前に今の公開の状態を確かめ、公開→非公開後に共有キャッシュから返さない（今の resolve のキャッシュは公開かどうかを持たず、`/r/default` は非公開も返すため）。既存 `/r/default` の方針は変えない。
6. **運用と文書:** grant 発行・取得・公開 resolve の回数と容量を制限。利用者ごとの発行数は DB で数える。個人カタログは private/no-store。経路は `/r/` と `/vrcurl/` の下に置き、名前が上流の保護で止まらないことを確かめる（3.2）。連携キーをアプリのログに出さない。プロキシのアクセスログには経路が数十日残るので、カタログの経路だけログから外すか、キーの寿命を短く保つことで受け入れるかを決め、監視・停止手順とともに用意する。DB 変更は setup-db.ts で冪等にし、秘密を Hasura の利用者向け API に公開しない。

### 5.2 KawaPlayer 側 — [#302](https://github.com/Mega-Gorilla/KawaPlayer/issues/302)

1. **任意モジュール:** 仮称 VHubLibrary。通信、個人状態、入力・一覧 UI を module 内に閉じる。Controller は認証を知らず、既存の URL interceptor を上書きして取り合わない。
2. **Editor と配線:** module の追加 / 無効化、UI の build-time wiring を既存規則で作る。公開リスト用の VRCUrl 配列は、検索と同じ `_resolvePool`（`/vrcurl/resolve/{i}` × 4,096）を使い、二重に焼き込まない。新 Udon は新しい子オブジェクトに置き、出荷済みオブジェクト上の UdonBehaviour 数を変えない。
3. **個人用 UI:** 専用 URL 欄と接続・手動更新・切断、自作 / お気に入り一覧、件数・上限・読み込み・エラーを用意。 URL 欄には連携 URL の前半を入れておき、決めた前半で始まる URL だけ受け付け、読み込んだら欄を元に戻す。欄を表示するたびに前半を入れ直す（6.5）。既存の配色・多言語化を使う。画面 / タブレットで自分の一覧を扱えるが、物理的に他人から見えないという意味ではない。
4. **応答の検証:** schema、pool、index、ID、型、件数、サイズ、名称の長さ・rich text を検証。1 件だけ取得し、接続変更・切断後の古い callback を無視する。失効を確認したら旧一覧を消して接続を要求する。
5. **選択と共有:** 選んだ項目の識別（`default/` ＋ `items[].id`）とともに `PlaylistLoader` へ渡し、応答の識別が一致したあと、既存の `BeforeUserLoadPlaylist`・入替確認・競合チェックへ委譲する。取得の URL と識別を分けて同期する作り（`SourceKey`）は、検索の計画の 5.2 のものを使う。解析・トラック構築・Fill の別実装を増やさず、必要なら既存処理に小さな共通入口を作る。非公開のリストは、応答で受け取った曲をその共通入口へ渡して共有枠に入れる（取得の URL なし、識別あり）。その枠の更新ボタンは働かせず、選んだ本人が選び直す形にする。確認の重複・Controller への認証追加はしない。
6. **文書と QA:** 最小対応 SDK でのコンパイル、Prefab / Network ID、既存プロジェクト更新を確認。PC / Quest と 2 アカウントで個人分離・共有・後入り・拒否を確認し、架空データの操作画像付きガイドへ反映する。

### 6.1 二種類の GET を分ける

| 用途 | 経路の例（案） | 認可と応答 |
| --- | --- | --- |
| 個人カタログ | `/r/library/{grant}` | キーによる限定閲覧。公開のリストは概要と番号、非公開のリストは曲まで入れた 200 JSON。private/no-store。利用者が入力した VRCUrl を使う |
| 選んだ公開リスト | `/vrcurl/resolve/{index}`（検索の計画と共用） | 公開情報のみ。キー不要。事前ベイクした URL から選び、既存 resolve と同じ曲の形式を 200 JSON で返す |
| 選んだ非公開リスト | （取得しない） | 個人カタログの応答に入っている曲を使う。番号の URL には載せない（6.6） |
| 動画の再生 | 既存 `/vrcurl/default/{index}` | 変更しない。選んだ曲を再生するときだけ利用 |

表 6. 使う経路（案）。

経路を `/r/` と `/vrcurl/` の下に置くのは、Udon からの取得が今の構成で通るのがこの 2 つの下だけだから（3.2）。`/r/library/{grant}` は、今の `/r/{pool}/{playlistId}` と同じ 2 区切りの形に収まる。`library` は pool の名前としては使わず、resolve の対象にしない。

個人キーは第1の経路だけで使う。第2の番号は秘密として扱わず、列挙されても個人の一覧・非公開リストを返さない。番号は使い回されることがあるので、**番号の URL は取得にだけ使い、どのプレイリストかは応答の `id` で見分ける。** 選んだときも、共有したあとの更新でも、枠を書き換える前に識別を照合し、違えばどの枠にも書かない。こうして、共有済みの source があとで別のリストを指しても取り違えない。照合の手順は検索の計画の 5.2 に合わせる。

![採らない案：リストごとの永久の番号。採る案：番号 12 でリスト A を読み、あとで番号 12 が B に使い回されても、更新のときに id が違うので枠を書き換えない](images/numbers.svg)

図6. 番号は使い回し、id で照合する（D4）。

カタログで曲まで用意するかは、公開かどうかで分ける。

- **公開のリスト:** カタログでは概要と番号だけを返す。曲の動画の番号（default プール）は、この時点では割り当てない。選んだときに `/vrcurl/resolve/{index}` が、今の resolve と同じ処理で割り当てて返す。
- **非公開のリスト:** 番号の URL に載せられないので、カタログの時点で曲ごとに動画の番号を割り当て、曲名と番号を応答に入れる（6.6）。選ぶ前に番号を用意するのは、この分だけである。対象は本人の自作で、grant が非公開を含むときに限り、D2 の上限に収まる分までとする。

公開リストを `resolve` プールへ登録する処理と、動画の番号の割り当ては分ける。将来ページ送りを足す場合も、受け取った cursor を文字列連結して VRCUrl に変換する案にはしない。

### 6.2 カタログの例（すべて架空）

```json
{
  "schemaVersion": 1,
  "resolverPool": "resolve",
  "grantExpiresAt": "2030-01-01T01:00:00Z",
  "total": 2,
  "returned": 2,
  "truncated": false,
  "items": [
    {
      "id": "SAMPLE_PLAYLIST_ID",
      "name": "サンプル A",
      "visibility": "public",
      "trackCount": 12,
      "resolveIndex": 42,
      "collections": ["created", "favorites"]
    },
    {
      "id": "SAMPLE_UNLISTED_ID",
      "name": "サンプル B",
      "visibility": "unlisted",
      "trackCount": 2,
      "collections": ["created"],
      "tracks": [
        { "index": 101, "title": "サンプル曲 1", "mode": 1, "provider": "youtube" },
        { "index": 102, "title": "サンプル曲 2", "mode": 1 }
      ]
    }
  ]
}
```

`total` / `returned` は両欄の重複を除いた件数。欄ごとの総件数が必要なら別フィールドを契約へ追加し、戻った配列長から全件数を推測しない。`grantExpiresAt` は表示の補助であり、サーバーが毎回期限を判定する。`visibility` は `public` か `unlisted`。`unlisted` の項目には `resolveIndex` が無く、`tracks`（resolve の `tracks` と同じ形）が入る。上限で曲を入れられなかった項目は `tracks` を省き、`tracksOmitted: true` にする。

選択先の成功応答は既存の `{ ok, id, pool: "default", name, tracks: [{ index, title, mode, provider? }] }` を基本にする。**応答の id が選択と違う場合は Fill より前に拒否する。** module / loader 間の共通入口でこの検証順序を守る。

### 6.5 連携 URL の入力を軽くする（D8）

VRChat では、実行中に文字列から VRCUrl を作れず、入力された VRCUrl を保存して次の訪問で使うこともできない。そのため、**連携 URL は、訪問のたびに利用者が入力する。** この制約は無くせない。入力が要るのは一覧を読むこの 1 本だけで、選んだリストの読み込みと共有は、焼き込んだ番号の URL で進む（図 5）。

作れなくなる障害ではないが、使い勝手ではいちばんの弱点になる。連携 URL は 60 文字前後あり、PC は貼り付けで済むが、VR と Quest では打つことになる。

![A 連携 URL を丸ごと貼る、B 前半を入れておき短いコードだけ打つ、C 検索の欄にコードを打つ、の 3 案を入力欄の見た目で比べた図](images/key-input.svg)

図7. 連携 URL の入力の 3 案（D8）。B に決定した。青い下線が、利用者が入力する部分。

| 案 | 利用者が入力するもの | 良い点 | 気をつける点 |
| --- | --- | --- | --- |
| A. 丸ごと貼る | 連携 URL の全体（60 文字前後） | 作りが最小。キーを長くできる | VR・Quest では実用にならない |
| **B. 前半を入れておき、短いコードだけ打つ**（決定） | コード 10〜12 文字 | 検索語を打つのと同じ手間。PC は丸ごと貼ってもよい | キーが短くなるので、寿命・回数制限・有効な数の上限で推測を防ぐ |
| C. 検索の欄と共用 | 検索の欄にコード 10〜12 文字 | 専用の欄・経路・結果の表示を、検索（#145）と共用できる | 検索語は表示してよいが、コードは表示にもログにも出せない。扱いを分ける必要がある。検索の実装が前提 |

表 9. 連携 URL の入力の案。

**決定（2026-11-11）: B で進める。** 決めた前半で始まる URL を受け付けるので、PC では A のように連携 URL を丸ごと貼ることもできる。C は初期版では採らない。検索（#145）を実装したあとで欄を共用したくなったら、改めて判断する。コードの文字数（10〜12 文字）は、PoC で推測に対する強さを確かめてから確定する。

B の作り:

- **前半を入れておく。** 入力欄に、連携 URL の前半（B なら `https://playlist.vrc-hub.com/r/library/`）を入れておき、利用者は続きにコードを打つ。検索の計画（[145-vhub-search](../145-vhub-search/README.md)）が採っている、入力欄に URL の前半を入れておく方式と同じ。
- **決めた前半で始まる URL だけ受け付ける。** それ以外の URL は読み込まない。
- **読み込んだら、欄をすぐ元に戻す。** コードを画面に残さない。エラーの文やコピー欄にも出さない。
- **欄を表示するたびに、前半を入れ直す。** 無効のまま読み込まれた入力欄には初期の値が入らないことがあるので、一覧の板を開くたびに入れ直す。
- **コードは打てる形にする。** 大文字と小文字を区別せず、見分けにくい字（0 と O、1 と I など）を使わない 10〜12 文字。Web では 4 文字ずつ区切って見せ、連携 URL の全体をコピーするボタンも置く。区切りの `-` は、サーバーが読むときに無視する。
- **短いコードの安全は、長さだけに頼らない。** 寿命（D1）、有効なコードの数の上限、IP ごとと全体の回数制限（D5）を合わせて、当て推量が現実的でないことを PoC で数字にして確かめる。足りなければ文字数を増やす。

使えない手もある。検索の応答は、次のページや画像を番号で返し、焼き込んだ番号の URL で読ませることで、2 回目からの入力を無くしている。番号の URL は誰でも順に読めるので、この手は公開の中身にしか使えない。本人の一覧や非公開のリストを番号に載せることはしない（D7 の B 案は、この手では解けない）。

### 6.6 非公開のリストの読み込みと共有（D7＝B）

非公開（URL 限定）のリストは、URL を知っている人だけが読める。番号の URL（`/vrcurl/resolve/{i}`）は誰でも順に読めるので、非公開のリストは載せられない。そこで、連携 URL の応答に曲まで入れて返し、選んだらその曲をそのまま共有枠に入れる。

| | 公開のリスト | 非公開（URL 限定）のリスト |
| --- | --- | --- |
| 一覧の応答に入るもの | 概要と番号 | 概要と曲（resolve と同じ形） |
| 選んだときの読み込み | 番号の URL をもう 1 回読む | 読まない。応答の曲を使う |
| 全員へ同期するもの | 曲、番号の URL、識別 | 曲、識別（取得の URL なし） |
| 後から入った人 | 再生できる | 再生できる |
| 更新ボタン | 番号の URL を読み直す（識別を照合） | 働かない。選んだ本人が一覧から選び直す |
| 同じリストを VRChat用URL で貼ったとき | 識別が同じなので同じ枠になる | 同じ枠になり、その枠は URL で更新できるようになる |

表 10. 公開のリストと非公開のリストの扱いの違い。

- **含めるかは利用者が選ぶ。** 連携 URL を発行するとき、非公開のリストを含めるかどうかを選べる。含めない連携 URL では、非公開のリストは一覧に出ない。
- **対象は自作だけ。** 他人の非公開のリストは、お気に入りに入っていても出さない（今の Web の一覧と同じ）。
- **上限を置く。** 曲まで入れると応答が大きくなる。新しい順に、上限（D2）に収まる分だけ曲を入れる。入らなかったリストは名前だけ出し、VRChat用URL を貼れば読み込めると案内する。今の規模では、非公開のリストは 1 人あたり多くて十数件、ほとんどの人は数件。
- **共有すると、その場の全員に届く。** 共有枠に入れた曲と識別（`default/{id}`）は全員へ同期される。今 VRChat用URL を貼って読み込むときに、URL が全員へ同期されるのと同じ範囲。共有の前の確認に、非公開のリストであることを出す。
- **サーバーの負荷を確かめる。** 曲を返すには、曲ごとに動画の番号（default プール）を割り当てる。検索の計画が「応答に曲まで入れる」案を採らなかったのは、この負荷のため。Library の一覧は本人が手動で読むときだけで、対象も本人のリストに限られるが、応答の時間は PoC で測る。

## 7. 順序と判断ゲート

![PoCとAPI契約の成功後にVHub側とKawaPlayer側を実装し、統合QAとガイド更新を経て限定公開する順序](images/roadmap.svg)

図8. PoC が通るまで製品の契約や本番設定を確定しない。サーバーとクライアントの実装を分けても、契約・サンプルは共通にする。

**実装の順（決定、2026-11-11）:** 検索（#145）を先に実装する。`/vrcurl/resolve/{i}`・`_resolvePool`・`SourceKey` は検索が作り、Library はそれを使う。Library の PoC（Gate A）は、検索の番号の仕組みが動いてから始める。

1. **Gate A — [#301](https://github.com/Mega-Gorilla/KawaPlayer/issues/301):** 架空データと使い捨て環境で取得→選択→共有を試す。実装中の Unity / 本番を勝手に操作しない。PC / Quest、URL・ログ・同期の境界、番号の使い回しと識別の照合、API 形式、キーの期限・失効を記録し D1〜D8 を更新。対象範囲（D7＝B）、番号の共用（D4）、連携 URL の入力（D8＝B）は決まっている。コードの文字数は、この PoC で確かめて確定する。
2. **製品実装 — [VHub #317](https://github.com/kisaragi-official/vhub-playlist/issues/317) / [KawaPlayer #302](https://github.com/Mega-Gorilla/KawaPlayer/issues/302):** Gate A の契約で実装する。モックの開発は並行でもよいが、未検証の方式で本番公開しない。
3. **Gate B — 親 [#300](https://github.com/Mega-Gorilla/KawaPlayer/issues/300):** 以下の統合 QA、案内・画像・運用手順、停止経路を確認してから限定公開。ユーザー向けの操作と制作者向け設定を区別する。

**No-Go:** 秘密・容量・操作性を満たさなければ親 issue へ戻す。VRChat のパスワード、表示名照合、Cookie 流用、秘密を同期する近道へ変更しない。従来の VRChat用URL の手動入力は維持する。
